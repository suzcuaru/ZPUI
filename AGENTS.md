## 1. Что такое ZPUI (кратко)

**ZPUI** — настольное приложение для Windows, которое одним нажатием включает обход блокировок Discord, YouTube и других ресурсов через движок [zapret2](https://github.com/bol-van/zapret2) (апстрим проекта zapret того же автора; единственный поддерживаемый движок — legacy zapret1 Flowseal выведен). Дополнительно: SOCKS5-прокси и Xbox DNS для раздачи обхода на другие устройства в домашней сети, встроенный Telegram MTProto-прокси (мост — отдельный дочерний компонент `ZPUI-TgProxy.exe` из родной кодовой базы [Flowseal/tg-ws-proxy](https://github.com/Flowseal/tg-ws-proxy), исходники в соседнем проекте воркспейса `../ZPUI-TgProxy`; ZPUI управляет им через супервизор `internal/tgproxy`).

- **Платформа:** только Windows 10/11 (x86 и x64).
- **Лицензия:** проприетарная EULA (закрытое ПО, строгие правила использования/распространения). Базовый функционал бесплатен; облачные сервисы — по подписке «ZPUI Plus» (аккаунт через Telegram-бота). Телеметрия (канал данных ZPUI Sync) включена по умолчанию у всех устройств, включая неавторизованные; отключается пользователем тумблером «Канал данных» (см. Концепцию §8).
- **Стек:** Go (Wails v2) + React 18 (Vite) + SQLite + кастомные Wails-инсталляторы (установщик/обновлятор/удалятор).
- **Подробно:** см. [`Документы/Концепция.md`](./Документы/Концепция.md).

## 2. Технологический стек

### Backend (Go)

| Компонент | Технология | Назначение |
|---|---|---|
| Язык | **Go 1.26+** | основная логика (см. `go.mod`) |
| Каркас | **Wails v2** | связка Go ↔ web-фронтенд, нативное WebView2-окно |
| БД | **modernc.org/sqlite** (pure Go, без cgo) | история мониторинга, события |
| Логи | `log/slog` + собственный `internal/logger` | структурные логи в файл |
| Сеть | stdlib `net/http`, `net` | HTTP-клиент, SOCKS5, DNS |
| Win32 | `golang.org/x/sys/windows`, `golang.org/x/sys/windows/registry` | трей, реестр, named mutex |
| Движок обхода | внешний `winws2.exe` (zapret2) через дочерний процесс | модификация пакетов через WinDivert |

### Frontend (web/)

| Компонент | Технология | Назначение |
|---|---|---|
| Каркас | **React 18** | UI |
| Сборщик | **Vite 5** | дев-сервер + production-бандл |
| Роутинг | **React Router v6** | навигация по вкладкам |
| i18n | собственный `useT` + `locales/{ru,en}.json` | локализация |
| Стили | чистый CSS + CSS Custom Properties | дизайн-система без Tailwind |
| Тесты | **Vitest** | unit-тесты утилит и хуков |

### Инфраструктура

| Компонент | Технология | Назначение |
|---|---|---|
| Инсталляторы | **Wails-приложения** (`cmd/setup`, `cmd/updater`, `cmd/uninstall` + `internal/pkginst`) | установщик / тихий обновлятор / удалятор (NSIS выведен из эксплуатации) |
| CI | **GitHub Actions** | `.github/workflows/release.yml` (ubuntu-latest) |
| Сборка | `build.bat` | оркестрация полной сборки |
| Релиз | `release.bat` | помощник публикации релиза |
| Зеркало | Яндекс.Диск | резервный канал обновлений ZPUI (фолбэк при недоступности сервера управления) |

Подробно — в [`Документы/Архитектура.md`](./Документы/Архитектура.md) §1.

## 4. Команды сборки и проверки

### Backend (Go) — из корня репозитория

```bash
go vet ./...        # статические проверки — ДОЛЖНО проходить
go test ./...       # unit-тесты (config, monitor, zapret, logger, updater)
go build ./...      # компиляция всех пакетов
```

Запускать после **любого** изменения Go-кода.

### Frontend (web/) — из папки `web/`

```bash
npm install         # установка зависимостей (после изменения package.json)
npm run build       # production-сборка (vite) — ДОЛЖНО проходить
npm test            # vitest однократно
npm run test:watch  # vitest в watch-режиме
npm run dev         # дев-сервер на :3000
```

### Полная релизная сборка

```bash
build.bat           # build frontend → Wails core → модули → build/dist/
```

Требует `go`, `node` и `wails` CLI на PATH.

### Релиз и резервные копии

```bash
release.bat         # интерактивный помощник релиза (tag, push, заметки)
..\backup-all.bat   # бекап всех 4 проектов воркспейса (из корня воркспейса)
backup.bat          # точечный бекап этого проекта (обёртка ..\backup.ps1)
```

Снапшоты — в `../ZPUI-Backups/<проект>/snap-*`: 5 сырых + 5 архивов на проект
(ротация трогает только имена `snap-*`); исключения — `.git`, `node_modules`,
`build`, `dist`, `*.exe`, `*.db`, `logs`, `uploads`, `config.json`. Правила — в [`../README.md`](../README.md).

### Воркфлоу внесения изменений (батники — часть цикла)

1. **Нетривиальная задача — сначала спека:** конвейер SDD (скилл `zpui-sdd`): спека в `Документы/Задачи/` → уточнения → план/таски → реализация → верификация по критериям приёмки → доки. Точечные фиксы и косметика — без спеки.
2. **ОБЯЗАТЕЛЬНО до любых правок — бекап:** `backup.bat` этого проекта или `..\backup-all.bat` (все проекты воркспейса). Правки без сделанного бекапа не начинать — это не рекомендация, а обязательное требование.
3. Правки + проверки: `go vet ./...`, `go test ./...`, `cd web && npm run build`.
4. **После выполнения задач** — `build.bat` (полная сборка: frontend → Wails core → модули → `build/dist/`).

## 5. Конвенции кода

### Общие

- **Без комментариев**, кроме случаев, когда логика действительно неочевидна (и тогда — короткий поясняющий).
- Имена пакетов и файлов — короткие, строчные, английские.
- Файлы группы — с префиксом: `app_zapret.go`, `app_proxy.go` и т. п.

### Backend (Go)

- Frontend → backend вызовы идут **только** через `web/src/api.js` (карта маршрутов). Новый эндпоинт = (1) добавить в карту в `api.js` + (2) реализовать как `func (a *App)` метод в `internal/app/`.
- Ответы API — единый формат через хелперы из `internal/app/app_api_types.go`:
  - `okResp(data)` → `{"status":"ok", ...data}`
  - `errResp(msg)` → `{"error":"..."}`
  - фронтенд проверяет наличие поля `error`.
- Долгие операции пушат прогресс через `runtime.EventsEmit("событие", {...})` — фронтенд слушает через `runtime.EventsOn`.
- Логи — через `slog` (не `fmt.Println`, не `log`).
- Ошибки возвращаются явно (`if err != nil`), не паникуем.

### Frontend (React)

- Переиспользуемая логика — в `web/src/hooks/` (`usePolling`, `useDebouncedSave`, `useNow`, `useUpdateCheck`, `useUpdateFlow`, `useWailsEvent`, ...).
- Базовые кирпичики UI — в `web/src/components/ui/` (`Row`, `Switch`, `Modal`, `Button`, `Card`, ...). **Не дублируй** стили; используй токены из дизайн-системы.
- **Все** пользовательские строки — через i18n (`useT`/`t('...')`). Никаких захардкоженных русских строк в JSX. Вне React — `tr()`.
- Стили — через CSS Custom Properties из дизайн-системы. **Никаких хардкод-цветов и магических чисел.**
- API-вызовы — только через `api(method, route, body)` из `web/src/api.js`. Не вызывай `window.go.app.App.*` напрямую из компонентов.
- Состояние настроек — `config.json` единственный источник истины. Сохранение через `useDebouncedSave`.

### Версионирование

- **ZPUI core** — SemVer, источник истины — `versions.txt` (поле `zpui=`), бампится вручную. `build.bat` читает версию оттуда и инжектит через `-X main.version=...`; `components/service/version.txt` генерируется сборкой.
- `tgproxy` — версия берётся из `__version__` апстрима (`../ZPUI-TgProxy/tg-ws-proxy/proxy/__init__.py`) и инжектится ldflags.
- `versions.json` — собираемый артефакт (`zpui`, `tgproxy`, `service`), не редактируется вручную.

### CHANGELOG — два журнала

- **[`CHANGELOG.md`](./CHANGELOG.md) — для пользователей.** Показывается в клиенте и на GitHub при обновлении. Правило: **кратко, просто, без воды** — человек за 10 секунд должен понять, что изменилось в его программе. Одна строка на изменение. Запрещены любые технические термины (кэш, гонка, рендер, биндинг, маршрут, SHA-256, atomic, race condition…), имена файлов/пакетов/функций, внутренняя кухня и длинные пояснения «как устроено». Плохо: «Исправлен race condition в tray.go»; хорошо: «Программа больше не зависала при сворачивании». Формат всех версий — секция `### Кратко`: заголовок `## vX.Y.Z`, одна строка на тему.
- **[`CHANGELOG-DEV.md`](./CHANGELOG-DEV.md) — журнал разработки (для владельца и агентов).** Полная техническая информация по всем версиям и внутренним батчам: даты, файлы:строки, причины, схемы решений, замеры — без урезаний и сжатия. Пополняется при каждом батче правок (дата + суть). Детальный текст версии перед сокращением в CHANGELOG.md переезжает сюда целиком.
- Пользовательский CHANGELOG.md не дублировать в AGENTS.md, README или коммит-сообщениях; полная история версий и батчей живёт в CHANGELOG-DEV.md и `git log`.

## 7. Что НЕЛЬЗЯ делать

- **Коммитить без проверки:** `go vet ./...` и `npm run build` обязаны проходить.
- **Вносить правки без предварительного бекапа** (`backup.bat` / `..\backup-all.bat`) — бекап перед началом изменений обязателен.
- **Захардкоживать** цвета, размеры, строки вне i18n.
- **Менять размеры окна** (адаптив 900–1280×650–720, минимум 900×650, безрамочный режим без maximize — `main.go` + `winsize_windows.go`) — это сознательное продуктовое решение.
- **Добавлять сбор данных сверх каталога секций ZPUI Sync и любую рекламу** — нарушает продуктовые принципы (см. [`Документы/Концепция.md`](./Документы/Концепция.md) §8). Телеметрия — только через зашитый каталог секций канала, для умного подбора/диагностики; передача включена по умолчанию (в том числе без аккаунта — политика 11.2026) и отключается юзер-тумблером «Канал данных». Новые секции/поля сверх каталога — только с явного согласования с пользователем.
- **Менять лицензию** без явного согласования пользователя.
- **Бампить версию модуля** без реальных изменений в нём.
- **Поддерживать macOS/Linux** — не в дорожной карте (WinDivert Windows-only).
- **Писать комментарии** где логика очевидна.
- **Коммитить секреты, ключи, токены** — никогда.
- **Менять формат API-ответов** (оставаться на `okResp`/`errResp`).
- **Использовать HTTP-сервер** для связи frontend↔backend — только Wails bindings через `api.js`.
- **Менять `versions.json` вручную** — он собираемый.
- **Форсить/ amend / интерактивный rebase / пустые коммиты** без явного запроса пользователя.

## 8. Архитектурные принципы (кратко)

1. **Единый процесс:** ZPUI.exe содержит и backend (Go), и фронтенд (WebView2), и сетевые серверы (SOCKS5, DNS), и порождает дочерний `winws2.exe`.
2. **Backend — источник истины:** состояние хранится в `config.json` и SQLite. UI — отражение.
3. **Связь frontend↔backend:** только через Wails bindings (`window.go.app.App.*`), обёрнутые в `web/src/api.js`. Никаких HTTP/REST между ними.
4. **Движок — внешний процесс:** zapret2 (`winws2.exe`) управляется как дочерний процесс, а не линкуется в Go.
5. **Асинхронщина:** долгие операции пушат прогресс через `EventsEmit`/`EventsOn`, не блокируют UI.
6. **Безопасность:** UAC-elevation для WinDivert и DNS:53; проверка SHA-256 скачиваемых архивов; наружу — только каталог диагностических секций ZPUI Sync (включён по умолчанию, отключается «Каналом данных» в настройках); аккаунт-данные — только в аккаунт-операциях.
7. **Один экземпляр:** named-mutex гарантирует единственный запущенный ZPUI.
8. **Корректное завершение:** `OnShutdown` останавливает winws, закрывает серверы, flush'ит логи.

Подробно — в [`Документы/Архитектура.md`](./Документы/Архитектура.md).

## 9. Доменные правила (кратко)

- **Движок zapret** имеет состояния: `stopped / starting / running / error / restarting`. Лимит рестартов: 5 за 60 сек, далее — `error`.
- **Автоподбор** перебирает стратегии, выбирает с максимальной доступностью; приемлемый минимум — 70%.
- **AutoSwitch** срабатывает при доступности ниже порога (дефолт 60%) ≥ 2 подряд сэмплов, с cooldown 10 мин.
- **Доступность** = TCP + TLS + HTTP по пулу ресурсов, скользящее окно 3 сэмпла для UI.
- **Мастера первого запуска и выбора движка нет** (удалены 14.11.2026, `config.wizard.completed` больше не существует): при старте без движка приложение само скачивает zapret2 по авто-источнику (сервер + GitHub, побеждает свежая версия), ставит его и запускает — прогресс на стартовом экране.
- **Обновления** (см. Бизнес-логика §8): проверки **только при запуске** (по тумблеру `auto_update_check`), без интервалов; результаты кэшируются в `updateFlags` (трей/панель читают без сети). **ZPUI** — источники по приоритету: **сервер управления** (`GET /api/v1/updates/zpui` → файл из `uploads/`; авторизованные устройства) → **Яндекс.Диск** (фолбэк только при недоступности сервера; неавторизованные — сразу Яндекс). Ответ сервера «обновлений нет» — окончательный. «Что нового» — из `notes` публикаций на сервере (`GET /api/v1/updates/zpui/versions`); GitHub для приложения не используется. Пакет обновления — **тихий обновлятор** `ZPUI-Update-<v>.exe` (кастомный Wails-обновлятор: `cmd/updater` + `internal/pkginst`, собирает `build.bat`): без страниц/подтверждений гасит ZPUI+winws, накатывает файлы поверх, данные и zapret не трогает. SHA-256: из манифеста (сервер) / по `checksums.sha256` (Яндекс) → «Установить» → приложение закрывается, Wait-Process-помощник запускает установщик. **Zapret (zapret2)** — единый канал `updates_source`: «Авто» = сервер (`/updates/zapret2`) + **GitHub** (релизы bol-van/zapret2, побеждает свежая версия; Яндекс из цепочки убран); установка ин-апп через `InstallZapretEngine`/`InstallDistArchive` (arch-aware: 32-битный процесс ставит binaries/windows-x86 с WinDivert32.sys, 64-битный — windows-x86_64 с WinDivert64.sys) с бэкапом состояния и откатом. В трее — пункты «Обновление ZPUI — скачать» / «Обновление запрета — скачать» (по флагам доступности).
- **Автозапуск приложения с Windows** реализован через **задачу Планировщика заданий** (`schtasks /SC ONLOGON /TN ZPUI /TR "\"...exe\" --hidden" /RL HIGHEST`). `/RL HIGHEST` даёт запуск с правами админа **без UAC** при входе — это сознательное продуктовое решение (ZPUI требует админа для WinDivert/DNS:53). Запись НЕ видна во вкладке «Автозапуск» Диспетчера задач (только в Планировщике заданий) — состояние читается напрямую из задачи: `GetAutostartStatus()` парсит `schtasks /Query /TN ZPUI /XML` (языконезависимо: наличие `<Task>` + `<Settings><Enabled>`). **Состояние автозапуска НЕ хранится в `config.json`** — единственный источник истины система. `syncAutostartSystem()` на старте мигрирует прежнюю Run-key схему на задачу и чистит устаревшие артефакты. `ensureAdmin()` в `main.go` отвечает за повышение при ручном запуске. Старая схема `HKCU\...\Run` оставлена только для чтения/очистки при миграции.

Полные правила — в [`Документы/Бизнес-логика.md`](./Документы/Бизнес-логика.md).

## 10. CI/CD

Файл `ci.yml` в репозитории отсутствует — проверки (`go vet ./...`, `go test ./...`, `cd web && npm run build`) выполняются локально перед коммитом.

### `release.yml` (ubuntu-latest)

**Важно:** этот job **НЕ собирает** бинарники (Windows-нативная сборка — Wails-приложение и Wails-инсталляторы — на Ubuntu невозможна). Он:

1. Реагирует на tag `v*.*.*`.
2. Берёт артефакты из корня репозитория — подготовлены локально `build.bat` + `release.bat` и **закоммичены** (`ZPUI.exe`, `ZPUI-x86.exe`, `ZPUI-Setup-*.exe`, `versions.json`, файлы списков). Без них workflow падает с явной ошибкой — молчивого пропуска релиза нет.
3. Формирует GitHub Release (установщик + portable zip, описание из CHANGELOG).

## 11. Версии модулей

Версия сервиса — `versions.txt` (поле `service=`), ложится в `components/service/version.txt` в деревьях dist. ## 15. Проектные агенты (`.zcode/agents/`)

Оркестратор (основной ZCode-агент) принимает задачи, дробит их и раздаёт профильным агентам; сам делает финальную сборку (`build.bat`), коммиты (по запросу) и сводит отчёты.

> **Главное правило оркестрации (решение владельца 14.11.2026): чат-оркестратор сам код НЕ пишет.** Он анализирует, пишет спеку/контракты, раздаёт задачи профильным агентам (`zpui-go-dev`, `zpui-react-dev`, …), принимает отчёты, верифицирует результат (grep-маркеры правок: `git status` врёт для gitignored `internal/` и `web/src/`) и делает финальные проверки/сборку. Реализацию любой задачи — агенту; исключение — точечный однострочный фикс, когда диспетчировать дороже, чем сделать (и тогда пометить в отчёте). Файл роли: `.zcode/agents/orchestrator.md`.

| Агент | Роль |
|---|---|
| `zpui-go-dev` | Go-код: internal/*, cmd/*, ../ZPUI-Server/control/api. Проверки: go build/vet/test своего модуля. |
| `zpui-react-dev` | web/, ../ZPUI-Mockups, ../ZPUI-Server/control/api/adminweb: страницы, компоненты, стили (токены, i18n, порядок хуков!). Эталон кнопок — upd-card в SettingsPage. |
| `zpui-qa` | Тест-планы и живые E2E (curl к control ../ZPUI-Server на :8080, DEMO_MODE), негатив/границы, баг-репорты. Код не меняет. |
| `zpui-doc-keeper` | Документация: CHANGELOG (текущая версия), Документы/*, ../ZPUI-Server/README, AGENTS.md §14. Код не меняет. |
| `zpui-net-eng` | Сеть/инфраструктура ../ZPUI-Server: deploy/compose, guard/edge, VPN/TLS/Tailscale, порты. |

Формат: `<repo>/.zcode/agents/<name>.md` с frontmatter name/description/color/model/thoughtLevel/injectAgentsMd: true (как `test.md`). После создания файлы видны в Settings → Subagents и доступны основному агенту как subagent_type по имени.

Правила взаимодействия: Go и React код не пересекаются (разные папки); QA и док-кипер код не меняют; финальные проверки всего проекта (`go vet ./...`, `go test ./...`, `npm run build`, `build.bat`) — всегда на оркестраторе.

**Полная агентская логика** (декомпозиция, контракты, dispatch, эскалация), возможности harness и использование **OpenCode** как бесплатного воркера (`opencode run -m opencode/hy3-free "...")` — скилл `zpui-orchestration` (`.agents/skills/zpui-orchestration/SKILL.md`). Подключать при любой многосоставной задаче и словах «поручи агентам/команде».
