# Бизнес-логика ZPUI

> Документ описывает доменные правила, состояния, сценарии и алгоритмы принятия решений в ZPUI. Это НЕ техническая архитектура компонентов (см. [`Архитектура.md`](./Архитектура.md)) и НЕ список кнопок (см. [`Функции.md`](./Функции.md)), а **правила поведения продукта**: в каких состояниях может находиться система, при каких условиях происходят переходы, как выбирается стратегия, как принимается решение «работает/не работает».

---

## 1. Доменные сущности

| Сущность | Описание | Где хранится |
|---|---|---|
| **Стратегия (Strategy / Preset)** | Именованный набор аргументов для `winws2.exe`: фильтр-списки, Lua-функции и т. п. | `zapret/strategies/*` или код |
| **Ресурс (Resource)** | Цель проверки доступности: `discord.com`, `youtube.com`, `discord.gg`, и т. д. | `config.resources[]` |
| **Состояние движка (EngineState)** | `stopped` / `starting` / `running` / `error` / `restarting` | runtime App |
| **Доступность (Availability)** | Процент ресурсов из пула, доступных в данный момент (0–100%) | computed из `blockcheck` |
| **Порог AutoSwitch (Threshold)** | Значение доступности, ниже которого триггерится автопереключение | `config.autoswitch.threshold` |
| **Профиль пользователя** | Набор предпочтений: тема, язык, интервал мониторинга, автозапуск, уведомления | `config.json` |
| **Событие (Event)** | Записываемое действие: старт zapret, смена стратегии, обновление, срабатывание AutoSwitch | SQLite `events` |

## 2. Состояния движка zapret

```
                 ┌──────────┐
                 │ stopped  │◄──────────────────────────┐
                 └────┬─────┘                            │
                      │ user: Start                      │
                      ▼                                  │
                 ┌──────────┐   error (timeout/      ┌───┴──────┐
                 │ starting │───crash/antivirus)────►│  error   │
                 └────┬─────┘                         └────┬─────┘
                      │ winws ready                         │ user: retry
                      ▼                                     │
                 ┌──────────┐    crash (with restart   ┌────┴──────┐
        ┌───────►│ running  │◄───budget left)──────── │restarting │
        │        └────┬─────┘                         └───────────┘
        │             │ user: Stop / shutdown              ▲
        │             │                                     │
        └─────────────┘                                     │
   auto-restart success                            crash detected
```

### Правила переходов

- **`stopped → starting`**: пользователь нажал «Старт», ИЛИ AutoSwitch инициировал, ИЛИ стартовый экран применил стратегию, ИЛИ автозапуск при старте системы.
- **`starting → running`**: `winws2.exe` запущен, процесс жив > N секунд (стабилизация), драйвер WinDivert загрузился.
- **`starting → error`**: процесс упал в первые секунды, WinDivert недоступен (антивирус удалил), отсутствие прав админа.
- **`running → restarting`**: процесс упал, счётчик рестартов < лимита (по умолчанию 5 за 60 сек).
- **`restarting → running`**: успешный рестарт.
- **`restarting → error`**: лимит рестартов исчерпан — считается устойчивый сбой.
- **`running → stopped`**: пользователь нажал «Стоп», ИЛИ приложение завершается.
- **`error → starting`**: пользователь нажал «Повторить», ИЛИ запущена диагностика и проблема устранена.

### Счётчик рестартов

- Окно: 60 секунд. Если за это время произошло ≥ 5 рестартов — движок переходит в `error`, пользователю показывается тост с рекомендацией открыть диагностику.
- Счётчик сбрасывается, если движок проработал стабильно > 60 сек.

### Внешний мониторинг движка (служба ZPUI)

Помимо рестартов внутри приложения, движок страхуют службы (см. §7.2):
на службе «zapret» включён SCM-recovery (перезапуск при сбое процесса),
watchdog службы ZPUI поднимает winws2 через `net start zapret`, если процесс
погиб при включённом автозапуске службы. При краше приложения движок **не
гасится** — переживает краш.

### 2a. Стабильность: супервизор фоновых модулей

Все фоновые циклы приложения (мониторинг, трафик, DNS-наблюдение, health движка,
SOCKS, серверные циклы, телеметрия, автообновление списков, служба и т. д.)
работают под супервизором:

- Паника в модуле не убивает приложение: сбой пишется в журнал, пользователю
  уходит тост (через общий хук ошибок), цикл перезапускается автоматически
  с нарастающей паузой: **1с → 5с → 15с → далее 60с**.
- Более **5 сбоев за 10 минут** — модуль помечается отказавшим (`failed`) и не
  рестартует до перезапуска приложения; счётчик подряд сбрасывается, если модуль
  прожил стабильно ≥5 минут.
- Статус модулей (`running` / `restarting` / `failed` / `stopped`) доступен
  через `/api/modules/status` и попадает в отчёт (секция «Фоновые модули»).
- Ранее «вечные» циклы (история трафика, netwatch, телеметрия сервера) теперь
  останавливаются при выходе приложения.

## 3. Выбор стратегии

### 3.1. Ручной выбор

Пользователь из вкладки «Стратегии» выбирает карточку → `SetStrategy(id)` → движок перезапускается с новыми аргументами → стратегия пишется в `config.activeStrategy` как активная.

### 3.2. Автоподбор (autoselect)

**Цель:** автоматически найти стратегию с максимальной доступностью для текущего провайдера/DPI.

**Два режима** (выбор — в модалке подбора, две плитки; кнопки «Запуск» в модалке нет):

- **«Умный»** — клик по плитке запускает сразу (см. §3.2a).
- **«Игровой»** — открывает второй шаг модалки: чек-лист стратегий для проверки
  (одна, несколько или все; по умолчанию отмечены все), кнопка запуска — внутри шага.

**Общий конвейер фаз** (показывается в модалке и на стартовом экране; фазы пишутся
в журнал, категория `autoselect`):

`operator` (определяем провайдера) → `server` (получаем данные с сервера) →
`local` (проверяем локальные данные) → `analyze` (анализируем) → `select`
(запускаем подбор). В игровом режиме фаза `server` пропускается.

**Общий цикл теста:** по списку кандидатов — на каждый: применить стратегию,
прогнать движок и замерить доступность/скорость/пинг, вернуть исходную стратегию;
лучшая по итогу применяется. Текущая стратегия восстанавливается между тестами,
прогресс — событиями `autoselect:event` / `autoselect:done`.

**Прерывание:** пользователь может отменить автоподбор в любой момент. Текущая тестируемая стратегия останавливается, восстанавливается предыдущая активная.

### 3.2a. Умный подбор (smart)

Доступен **всем пользователям** (гейта подписки нет) и работает **без сервера**.
Запускается вручную (плитка «Умный» в модалке подбора) и на стартовом экране —
там другого режима нет: фаза auto-select всегда умный подбор.

**Приоритет источников кандидатов:** сервер → локальные данные → все стратегии.

1. Приложение определяет своего оператора (isp-монитор); провайдер показывается
   в модалке и на стартовом экране и обновляется при смене сети. Оператор не
   определён — кандидаты без привязки к оператору.
2. **Сервер доступен** — операция v4 `strategies.top`: персональный план или топ
   по рейтингу «оператор × стратегия» (`strategy_samples`, окно 100 сэмплов,
   ротация 90 дней). Ответ дополняется усреднёнными игровыми баллами оператора —
   бейдж «игровая» появляется без локального прогона. Кандидаты — пересечение
   ответа с локальными `*.bat`.
3. **Сервер недоступен или не дал данных** — локальные данные оператора
   (баллы и доступность из истории `operator_strategies`), до
   `SmartLocalLimit` лучших.
4. **Локальных данных нет** — проверяются все стратегии.
5. **Порядок теста** — от обещающих к сомнительным: тир S → A → «неизвестные» →
   B → C; внутри тира — уверенные данные (≥3 сэмплов) раньше сырых, затем балл
   по убыванию группами по десяткам, затем локальная доступность. Серверный
   балл **строго больше 70**; стратегии с локальной историей ≥80 («здесь
   работает») участвуют даже без серверного балла; реальная локальная оценка
   <50 (D-тир) исключается, отсутствие истории — «неизвестно» (участвует по
   серверному баллу, иначе свежая установка отбрасывала бы весь топ). Протухшие
   данные (сэмпл старше 30 дней) не учитываются.
6. **Тест группами, промежуточные — без применения:** каждая группа — отдельный
   прогон движка с возвратом исходной стратегии. Лучший балл группы **≥70 —
   применяем и завершаем**; нет — следующая группа. Если данных нет вообще —
   перебор продолжается по всем стратегиям (диалога «подтвердите полный
   перебор» больше нет: умный подбор сам доходит до полного).
7. **Исследование:** если среди групп нет ни одной сырой/неизвестной стратегии —
   в хвост добавляется до двух серверных кандидатов с малым числом сэмплов.
8. Итог: применяется лучшая протестированная; если текущая стратегия свежая
   (автотест ≤14 дней) и ≥80 — в событиях пометка «ищем только лучше её», и она
   идёт первой в очереди.

### 3.2b. Игровой подбор (game)

- Второй шаг модалки — чек-лист всех стратегий (отмечены все; есть «Выбрать
  все» / «Снять все»); пользователь сужает список, кнопка «Запустить» — в шаге.
- Тестируются только выбранные стратегии, только на игровых ресурсах;
  применяется лучшая по игровому баллу. Фаза `server` пропускается.
- Если список получить не удалось — модалка сообщает об ошибке.

### 3.2.1. Пост-проверка YouTube при автоподборе

После применения лучшей стратегии автоподбора (режим проверки одной стратегии по ПКМ не затрагивается):

1. Запускается ytcheck (DNS-уровень): системный резолвер vs DoH + TLS-проба.
2. Если DNS-подмена НЕ обнаружена — в поток подбора пишется статус, всё.
3. Если обнаружена — через хук `SetYouTubeFixHook` приложение включает
   Xbox DNS (netsh + сброс DNS-кеша) и перепроверяет YouTube.
4. В поток пишутся оба результата («без DNS» / «с Xbox DNS»), состояние
   Xbox DNS сохраняется в конфиг и отражается в UI.

Экономный режим приостанавливает ytcheck вместе с ресурс-проверкой.

### 3.3. AutoSwitch (фоновое самоизлечение)

**Цель:** без участия пользователя реагировать на деградацию обхода.

**Параметры (в `config.autoswitch`):**

- `enabled` — вкл/выкл.
- `threshold` — порог доступности, ниже которого срабатывает (по умолчанию 60%).
- `cooldown` — минимальный интервал между срабатываниями (по умолчанию 10 минут), чтобы не «молотил».
- `strategyPool` — список стратегий для перебора (по умолчанию все).
- `consecutiveFails` — сколько подряд сэмплов ниже порога триггерят (по умолчанию 2, защита от единичных замеров).

**Алгоритм срабатывания:**

1. Monitor каждые N сек замеряет доступность.
2. Если `availability < threshold` — инкремент `failCounter`.
3. Если `failCounter ≥ consecutiveFails` И `time.Since(lastSwitch) ≥ cooldown`:
   a. Запустить `autoselect.Run()` на подмножестве `strategyPool`.
   b. Если найдена стратегия лучше текущей — переключиться.
   c. `tray.Notify("AutoSwitch: переключился на <strategy>")`.
   d. Сбросить `failCounter`, обновить `lastSwitch`.
4. Если доступность восстановилась — `failCounter` сбрасывается.

**Гарантия:** AutoSwitch НЕ отключает пользователя полностью. В худшем случае он переключает на лучшую из доступных стратегий; даже если ни одна не даёт 100%, пользователю обеспечивается максимум возможного.

## 4. Оценка доступности ресурсов

### 4.1. Что считается «ресурс доступен»

Ресурс считается доступным, если выполняется **комбинированный критерий**:

1. **TCP-коннект** к `host:443` успешен в течение таймаута (3 сек).
2. **TLS-рукопожатие** завершается без alert/RST.
3. **HTTP(S)-запрос** `/` возвращает ожидаемый код (200/301/302/4xx, не 0/5xx-от-провайдера).

Все три проверки должны пройти. Если любая падает — ресурс в этом сэмпле недоступен.

### 4.2. Расчёт процента

```
availability = (количество доступных ресурсов / всего ресурсов в пуле) * 100
```

С гистерезисом: единичный «провальный» сэмпл не считается мгновенным падением — используется скользящее окно из 3 сэмплов (медиана) для UI, чтобы дашборд не «дёргался».

### 4.3. Таймауты и обработка ошибок

- Каждая проверка идёт с таймаутом 3 сек (через `ctx`).
- Параллельные проверки ресурсов (`go func` для каждого).
- Сетевые ошибки (DNS, connection refused, TLS alert) → ресурс недоступен.
- Таймаут → ресурс недоступен (вероятно DPI глушит).

### 4.4. Пул ресурсов

Настраивается в `config.resources`. По умолчанию включает ключевые для продукта цели:

- `discord.com`, `discord.gg`, `discordapp.com`, `discordapp.net`
- `youtube.com`, `googlevideo.com`, `ytimg.com`
- (опционально) `twitch.tv`, `instagram.com`, пользовательские домены

## 5. SOCKS5-прокси: правила работы

### 5.1. Когда слушать

- Прокси-сервер стартует, **только** если пользователь включил тумблер «Прокси».
- Порт по умолчанию 1080; можно изменить.
- При смене порта сервер перезапускается.

### 5.2. Авторизация

- Без авторизации (по умолчанию) — доступ из локальной сети.
- С авторизацией (login + password) — рекомендуется, если ПК виден из недоверенной сети.

### 5.3. Что проксируется

- SOCKS5 CONNECT на любой host:port — обычное поведение SOCKS5.
- Прокси НЕ фильтрует контент, НЕ блокирует сайты, НЕ подменяет адреса.
- Весь исходящий трафик от клиентов идёт через сокеты ZPUI, которые перехватываются WinDivert (winws2.exe) на уровне драйвера — поэтому клиенты получают обход без установки zapret.

### 5.4. Ограничения

- Только TCP (SOCKS5 UDP ASSOCIATE поддерживается ограниченно).
- Не работает для клиентов, которые сами используют VPN поверх SOCKS (двойной обход может конфликтовать).
- Производительность ограничена пропускной способностью ПК-хозяина.

## 6. Системный DNS: правила работы

Модель DNS — `config.xbox_dns`: `{enabled, providers, custom, xbox_enabled}`
(см. §11). Источник адресов — `EffectiveServers()`: пресет xbox-dns.ru
(при `xbox_enabled`), включённые базовые провайдеры (`providers` — ключи
каталога `DnsProviders`) и пользовательские записи (`custom`). Локального
резолвера в приложении нет: в систему прописываются только **plain
IPv4-адреса** (записи с доменными адресами DoT/DoH пропускаются).

### 6.1. Применение

- Мастер-тумблер «Прописать DNS в систему» — адреса из `EffectiveServers()`
  применяются к **первичному физическому адаптеру** (лучший маршрут по
  умолчанию, не виртуальный): применение — dnsapi с netsh-фолбэком, чтение
  состояния — реестр, PowerShell не используется.
- Перед первым применением снимается прежнее состояние адаптера; выключение
  тумблера возвращает снимок.
- Активное состояние = факт «в системе прописаны наши DNS»; внешнее изменение
  DNS гасит тумблер. Живость адресов проверяется фоном: если серверы не
  отвечают (две проверки подряд), DNS снимается сам, система возвращается
  на прежние адреса, приходит уведомление.

### 6.2. Только IPv4

- IPv6-DNS в систему не прописывается (с v2.0.1), при применении статический
  IPv6-DNS адаптера снимается в DHCP.
- Легаси-поля прежней модели (primary/secondary) переносятся в
  `providers`/`custom` однократной миграцией при первом старте.

## 7. Первый запуск: бизнес-правила

> Классический пошаговый мастер заменён единым стартовым экраном (§7.1);
> ниже — правила, которые остались в силе.

### Шаг 1. Проверка системы

- ОС: Windows 10/11? Если нет — предупреждение, работа возможна, но не гарантируется.
- Разрядность: определяется x86/x64 (для arch-aware установки движка: 32-битный процесс ставит binaries/windows-x86 с WinDivert32.sys, 64-битный — windows-x86_64 с WinDivert64.sys).
- Права админа: если нет — нельзя продолжать (WinDivert требует). Показать инструкцию.
- Антивирус: если детектируется активный AV — предупреждение «добавьте ZPUI в исключения, иначе драйвер удалится».

### Шаг 2. Установка движка (zapret2)

- Если дистрибутив zapret2 присутствует и целостность в норме — пропуск шага.
- Если дистрибутив отсутствует/повреждён (в том числе legacy-каталог без
  winws2.exe) — приложение скачивает zapret2 само по updates_source «auto»
  (сервер управления + GitHub bol-van/zapret2; побеждает свежая версия),
  проверяет SHA-256, распаковывает с переносом пользовательских списков,
  ставит службу и запускает движок — без вопросов пользователю; процессы
  winws.exe прежнего движка гасятся.

### Шаг 3. Первичный автоподбор

- Запускается умный подбор (на стартовом экране — всегда он).
- Прогресс показывается в UI (конвейер фаз + провайдер).
- Если найдена приемлемая стратегия — применяется.

### Шаг 4. Финализация

- `config.activeStrategy` — записана выбранная.
- Дашборд открывается, движок запущен.

## 7.1. Единый стартовый экран (StartupScreen)

Первый запуск (и любой последующий) проходит единый стартовый экран,
проходящий 7 фаз последовательно:

1. **connect** — подключение к backend (ожидание Wails runtime)
2. **health** — проверка системных компонентов (winws2, WinDivert, библиотеки)
3. **check-service** — проверка состояния Windows-службы запрета
4. **install** — скачивание/установка zapret2 (если дистрибутива нет: авто-источник — сервер + GitHub, побеждает свежая версия)
5. **install-service** — установка/ремонт Windows-службы запрета (если нужно)
6. **auto-select** — умный подбор стратегии (всегда умный; если нет активной или она старше 7 дней)
7. **done** — переход на основной экран

Каждая фаза показывает прогресс-бар и статус; шаги пишутся во фронтовый журнал.
Ошибки отображаются inline, без модальных окон. На фазе подбора показывается тот
же конвейер фаз умного подбора (operator → server → local → analyze → select) и
провайдер. Если после установки движок не поднялся — приложение показывает
модалку сбоя с рекомендациями (HVCI) и кнопкой **«Переустановить запрет»**.

### Логика проверки службы Windows

- `CheckServiceHealth()` вызывается при фазе `check-service` — это проверка
  Windows-службы **запрета** (winws как служба), не службы ZPUI.
- Если служба не найдена → фаза `install-service` (установка/ремонт).

## 7.2. Служба ZPUI: автозапуск и watchdog

Отдельный процесс `ZPUI-Service.exe` (компонент приложения, ставится
установщиком; если его нет — приложение само ставит службу при первом запуске
с повышенных прав). Отсутствие службы — штатная ситуация: всё ниже работает
best-effort с фолбэком на прежнюю схему (локальное создание/удаление задачи).

**Что берёт на себя служба:**

- **Автозапуск с Windows:** тумблер «Автозапуск» в настройках управляет
  службой (команда `set-autostart`); служба создаёт/удаляет задачу
  Планировщика (`/SC ONLOGON /TN ZPUI /RL HIGHEST`) — задача остаётся
  механизмом запуска с правами админа без UAC, но источником истины тумблера
  становится состояние службы/задачи, а не config.json. При недоступности
  службы приложение создаёт/удаляет задачу локально (фолбэк).
- **«Запуск свёрнутым»:** служба передаёт `--hidden` при запуске
  (`set-hidden` — задача пересоздаётся с нужным аргументом).
- **Watchdog — восстановление после краша:** служба следит за процессом
  приложения. Если приложение исчезло, **не** сообщив о выходе/перезапуске/
  обновлении (`app-exiting` / `app-restarting` / `app-updating`), служба
  считает это крашем: пишет причину в реестр и
  перезапускает приложение через задачу Планировщика с паузами
  **1с → 5с → 15с**. Движок при краше приложения **не гасится** — он переживает
  краш (см. ниже).
- **Мониторинг движка (`engineWatch`):** служба следит за winws2. Если служба
  «zapret» установлена, её автозапуск включён, а процесса winws2 нет **два
  подряд тика** — движок поднимается через `net start zapret`; между попытками
  — cooldown 90 с. На самой службе «zapret» включён SCM-recovery (перезапуск
  при сбое процесса). Наблюдаемое состояние движка (installed/autostart/
  running/revives/last_revive) входит в IPC-статус службы (named pipe `status`).
- **Лимит крашей:** ≥5 крашей за час — цикл восстановления останавливается до
  ручного запуска приложения (статус `failed`).
- **Пауза watchdog** на время обновления приложения (`app-updating` с TTL).
- **Трей «Перезапустить»/«Выход»:** приложение уведомляет службу о
  перезапуске/штатном выходе, чтобы watchdog не счесть их сбоем.

**Состояние службы** — ветка реестра `HKLM\Software\ZPUI\Service`
(автозапуск, скрытый запуск, путь приложения, версия, статус, счётчики
крашей); журнал — `logs\service.log`. При старте приложение здоровается со
службой (`app-hello`), сверяет версию с ожидаемой и при несовпадении
обновляет exe службы из компонентов. Однократная миграция переносит решение
об автозапуске под службу (значение сверяется с фактом существования задачи,
чтобы выключенный автозапуск не превратился во включённый).

## 8. Обновления: правила

### 8.1. Обновление запрета (zapret2)

**Источники (движок — только zapret2; выбор в панели «Обновлений», `config.updates_source`):**

1. **Сервер управления (ZPUI Live)** — зеркало релизов апстрима: манифест с SHA-256
   (`GET /updates/zapret2`), zip раздаётся из `uploads/` (`/updates/zapret2/download`).
2. **GitHub / Гитхаб-прокси** — релизный zip bol-van/zapret2; «Гитхаб-прокси» ходит через
   зеркала gh-proxy.com → ghfast.top с прямым ретраем (те же хосты, что у сервера).

Режим «Авто»: сервер + GitHub, побеждает свежая версия. Явно выбранный
источник — единственный (без фолбэка). Яндекс.Диск из цепочки запрета убран.

**Когда проверять:**

- Автоматически **при старте** приложения (через 10с) и **периодически во время работы** — примерно раз в час со случайным сдвигом ±5 минут (чтобы клиенты не били в сервер синхронно); в экономном режиме интервал растягивается в 5 раз. Всё — **только если включён тумблер «Проверка обновлений»** (`auto_update_check`; тумблер действует и на фоновый цикл — включили на ходу, проверки начались без перезапуска). Этот же тумблер управляет уведомлениями.
- Результат проверки кэшируется в флагах (`updateFlags`) — трей и панель версий читают их без сетевых вызовов. Повторные находки не спамят: тост дедуплицируется по версии (`GetLastNotifiedVersion`), повторное событие за сессию не поднимает новую модалку.

**Уведомление о доступном обновлении:**

- Wails-событие `update:available` → модалка «Доступно обновление» с кнопками **«Установить»** (открывает модалку скачивания и сразу начинает загрузку) и «Позже»; дедупликация по версии за сессию.
- Windows-тост (если включены `notify_zapret_updates`).
- В **трее** появляется пункт «Обновление запрета — скачать» (скрыт, пока обновления нет); клик открывает окно приложения с модалкой скачивания.

**Процесс (всё внутри приложения, отдельной утилиты больше нет):**

1. Пользователь нажимает «Скачать» → открывается **немодальная-незакрываемая модалка** с прогресс-баром (закрыть во время скачивания нельзя).
2. zip качается в `%TEMP%\zapret-update.zip` (источник — сервер, при его недоступности GitHub).
3. После скачивания в модалке появляется кнопка **«Установить»** (модалку теперь можно закрыть и установить позже).
4. Установка: бэкап списков и стратегии в БД (`zapret_backup`) → полная остановка движка и драйверов WinDivert → распаковка с rename-трюком для занятых файлов → восстановление списков и службы → прогресс событиями `update:install` / `update:install-done`.
5. Ошибка на любом шаге → откат состояния из слепка; после прерванного обновления состояние восстанавливается при следующем старте.

### 8.2. Обновление ZPUI

**Схема: «скачали установщик → закрыли приложение → запустили установщик».** Никаких подмен бинарников и самообновления вспомогательного модуля.

**Источники (приоритет):**

1. **Сервер управления** — основной. `GET /api/v1/updates/zpui?device_id=` (манифест: версия, SHA-256, имя файла, notes, force, is_test; тестовые сборки — только тестировщикам) → файл раздаёт `GET /api/v1/updates/zpui/download?id=` из хранилища `uploads/` (публикация — через админку, `POST /admin/api/updates/<kind>/publish`). Версию сверяет клиент (`IsNewer`).
2. **Яндекс.Диск** — фолбэк только когда сервер **именно недоступен** (сеть, таймаут, 5xx, мусорный ответ): установщики `ZPUI-Setup-<версия>.exe` в корне публичной папки, версия из имени файла, максимальная. Ответ сервера «обновлений нет» — окончательный: Яндекс в этом случае не ищем. Неавторизованные устройства сервер не опрашивают (сразу Яндекс).
3. **GitHub / Гитхаб-прокси** — релизы `suzcuaru/ZPUI` (ассет `ZPUI-Setup-<v>.exe`, SHA — по приложенному к релизу `checksums.sha256`, его генерирует `release.yml`); «Гитхаб-прокси» — через зеркала gh-proxy.com → ghfast.top с прямым ретраем. Участвует в «Авто» третьим и доступен явным выбором.

**Селектор источника** (панель «Обновления», один на приложение и запреты): Авто / ZPUI Live / Яндекс Диск / GitHub / Гитхаб-прокси, хранится в `config.updates_source`. В «Авто» приоритет — ZPUI Live (решение владельца 12.11.2026).

**Пакет обновления:** тихий обновлятор `ZPUI-Update-<версия>.exe` (кастомный Wails-обновлятор, `cmd/updater` + `internal/pkginst`, собирает `build.bat`; NSIS выведен из эксплуатации). Без страниц и подтверждений: гасит ZPUI и winws, ждёт снятия блокировки, накатывает файлы поверх, обновляет версию в реестре, освежает только существующие ярлыки; данные пользователя (config.json, БД, логи) не трогаются (занятые файлы пропускаются). Обновлятор **не содержит запрет**: дистрибутив движка ставит и обновляет само приложение (авто-установка zapret2 при старте, §7). Если ZPUI не установлен — одно сообщение об ошибке и выход; установка с нуля — только полный `ZPUI-Setup`.

**Когда проверять:** как у zapret — при старте и раз в час во время работы (со сдвигом ±5 мин; в экономном режиме — раз в 5 часов), по тумблеру `auto_update_check`.

**«Что нового»:** из `notes` публикации на сервере — `GET /api/v1/updates/zpui/versions` (список опубликованных версий с заметками, тестовые — только тестировщикам). Показывается в модалке «Доступно обновление» и в панели версий по клику на версию. GitHub-релизы для приложения не используются; без сервера (или без входа) заметки недоступны — модалка показывается без них.

**Уведомления:** те же, что у zapret (`update:available`, тост, пункт трея «Обновление ZPUI — скачать»).

**Процесс:**

1. «Скачать» → незакрываемая модалка с прогрессом; файл качается в `%TEMP%` (имя — из манифеста сервера, иначе `ZPUI-Setup-<версия>.exe`).
2. Проверка SHA-256: с сервера — из манифеста, с Яндекса — по `checksums.sha256` корня Диска (записи генерирует `build.bat`); не совпало — ошибка, файл удаляется.
3. После скачивания — кнопка **«Установить»**: приложение закрывается, и через detached-помощника PowerShell (`Wait-Process -Id <pid>; Start-Process`) запускается установщик (он наследует права администратора ZPUI — UAC не появляется). Тихий установщик сам добивает оставшиеся процессы.
4. Обновление накладывается поверх старой версии без мастера.

**Force-обновление** (`force` в манифесте): приложение само скачивает файл с сервера, проверяет SHA-256 и устанавливает без участия пользователя (тем же Wait-Process помощником).

**Откат:** предыдущая версия остаётся в системе до успешной установки новой; при сбое достаточно запустить установщик заново (откат на сервере — `rollback_zpui` в настройках админки).

### 8.3. Раскладка Яндекс.Диска

```
/                              ← публичная папка (public_key)
  ZPUI-Setup-<версия>.exe         установщики ZPUI (плоско, без папок версий)
  checksums.sha256                хеши установщика и модулей (генерирует build.bat)
  components/report/              модульные обновления report.exe
  Zapret <версия>/                легаси для старых клиентов (новые берут zapret с GitHub)
  versions.json                   опционально, legacy для клиентов ≤1.6.x
```

Яндекс.Диск — канал ZPUI (фолбэк при недоступности сервера) и модульных обновлений. GitHub-релизы ZPUI остаются витриной (исходники, история), но установщик и заметки версий оттуда не берутся.

### 8.4. Откат версий запрета (ручная установка)

- Список версий: сначала зеркало сервера управления, при его недоступности —
  последние ~20 релизов GitHub (сортировка по версии, свежие сверху). Кэш
  5 минут; недоступность обоих источников — ошибка.
- URL на скачивание разрешается **в момент установки**: конкретная версия —
  с зеркала сервера (`?version=...`) или релиз по тегу GitHub (`v<версия>`).
- Установка — тот же `InstallFromZip`: бэкап состояния → остановка/удаление
  службы → распаковка → восстановление; при сбое — автоматический откат.
- После установки флаги обновлений сбрасываются (см. 8.2), интерфейс
  перечитывает панели версий и запускает свежую проверку.
- Порог входа: кнопка «Версии» на карточке Zapret; скачивание конкретной
  версии — `POST /api/updates/download-zapret-version {version}`.

### 8.5. ZAPRET 2 — единственный движок и его канал обновлений

Единственный движок запрета — zapret2 (winws2.exe, bol-van/zapret2); прежний
движок (zapret1 Flowseal, winws.exe) и выбор между ними выведены (решение
владельца 14.11.2026). Карточка «ZAPRET 2» в панели «Обновлений» работает по
обычному download/apply флоу: версия и заметки — из серверного зеркала
`GET /updates/zapret2` (манифест с SHA-256; сервер зеркалирует релизы апстрима —
проверено 14.11.2026: v1.0.7, архив байт-идентичен GitHub, внутри
`binaries/windows-x86_64` и `binaries/windows-x86`), в «Авто» участвует и GitHub
апстрима (побеждает свежая версия). Установка — распаковка dist с overlay поверх
каталога запрета с бэкапом прежнего; arch-aware: 32-битный процесс ставит
windows-x86 (WinDivert32.sys), 64-битный — windows-x86_64 (WinDivert64.sys).
Дистрибутив без winws2.exe при старте считается отсутствующим → авто-установка
zapret2 поверх (пользовательские списки сохраняются, процессы winws.exe гасятся).
При сбое движка — модалка с «Переустановить запрет» и `POST /api/zapret/restart`
(перезапуск с текущей стратегией).

## 8a. Аккаунт, подписка, туннель (ZPUI 3.0)

### 8a.0. Аккаунт = Telegram

- Аккаунт идентифицируется `tg_id`. Регистрация и повторный вход — кодом из
  приложения: `POST /api/v1/auth/code` (TTL 10 минут) → пользователь шлёт код
  боту → согласие на передачу данных Telegram → `POST /internal/auth/confirm`
  → клиент `GET /api/v1/auth/poll` получает Bearer-сессию (30 дней).
- Паролей нет: `password_hash` новых аккаунтов — сентинел `!tg`.
- Первый confirm создаёт аккаунт с **триалом 7 дней** (settings `trial_days`)
  и периодом `source=trial` в журнале `subscription_periods`.
- Лимит устройств — из плана (5); привязка/захват устройств — как раньше
  (`claimDevice`). Бот и веб-кабинет работают с теми же контрактами.

### 8a.1. Подписка ZPUI Plus

- Единый тариф `plus`: **150 ₽ / 30 дней / 5 устройств**, `vpn_access` и
  `tg_proxy` включены. Цена периода — `plan_prices` (месяц).
- Гейт «подписка активна»: `accounts.expires_at` (NULL — бессрочная).
  `subscription_periods` — журнал периодов (trial/purchase/admin/promo).
- **Продление стакается:** `AddPeriod` стартует новый период после
  `max(now, expires_at)`; первая подписка с триалом = 37 дней.
  Автопродлений нет; отказ = не продлевать (доступ до конца срока).
  Возвратов нет, кроме индивидуальных решений администратора (условия
  обслуживания, галочка перед оплатой в веб-кабинете).
- Напоминания: control отдаёт кандидатов (`GET /internal/subscription/reminders`
  — подписки, истекающие в 5 дней / истёкшие ≤30 дней), бот шлёт 5/3/1/0 дней
  и один раз о факте истечения (дедуп в локальном store). Клиент показывает
  тосты в последние 5 дней.
- Оплата: Robokassa (`POST /api/v1/payments/create` → redirect; ResultURL
  проверяет MD5 `OutSum:InvId:Password2`, активирует период, пушит боту
  `payment_paid`). Промокоды: процент, лимит использований, срок; метрика
  активаций в админке. Финансовый учёт: `GET /admin/api/finance/summary`
  (оплаты всего/по месяцам, ожидаемые продления месяца).

### 8a.2. Туннель (подписка для телефона — Happ)

- Туннель — часть подписки ZPUI Live. В приложении нет встроенного
  VPN-клиента: приложение управляет **подпиской для телефона** (клиент
  Happ, ссылки Reality); ноды и балансировка — на стороне сервера.
- Управление — в поповере профиля: ссылка/QR подписки устройства, перевыпуск
  токена (старый QR гасится), выпуск ссылки для дополнительного телефона
  (свой токен), отключение туннеля (своего или другого устройства аккаунта),
  трафик и лимиты тарифа.
- Клиентские маршруты — `/api/account/tunnel`, `/api/account/tunnel/rotate`,
  `/api/account/devices/tunnel-kill`, `/api/account/devices/tunnel-add`;
  доступ — при активной подписке.

### 8a.4. Балловая оценка стратегий (v3, 100 баллов)

- Балл складывается из четырёх компонентов (`internal/zapret/score.go`):
  **доступность общих ресурсов — 50, ключевые ресурсы — 15,
  пинг — 15, скорость — 20**. Нормировка фиксированная: пинг 20 мс →
  максимум / 150 мс → ноль; скорость 1 Мбит/с → ноль / 50 Мбит/с →
  максимум. Ключевые = голос/медиа Discord,
  видео YouTube, Steam (классификатор `isKeyTarget` по имени/URL цели).
- **Скорость вернулась в балл** (решение 29.10.2026, откат решения
  05.10.2026): замер — `netmetrics.Quick` (Яндекс) под активной стратегией,
  чем выше скорость, тем выше балл; доступность остаётся главным критерием.
- Замер не удался (пинг/скорость ≤ 0, ключевых нет) — вес компоненты
  остаётся у доступности: отсутствие данных не штрафует и не награждает.
  На сервере (`strategies/top`) формула своя — телеметрия ранжируется по
  средней доступности сэмплов; клиентская формула решает финальный выбор
  лучшей в прогоне.
- **Грейд** по баллу: S ≥ 90, A ≥ 80, B ≥ 65, C ≥ 50, D ниже; в UI рядом
  с баллом показывается слабейший компонент (`WeakestComponent`;
  компоненты без замера «слабейшими» не считаются).
- Применяется: сортировка результатов автоподбора, поле `score`/`grade`
  в `GetStrategies` (карточки вкладки стратегий).
- AutoSwitch и уведомления о падении доступности остаются на чистой
  доступности — это метрика «работает/не работает», балл — метрика выбора.

### 8a.5. Игровой режим стратегий

- **Игровой балл — отдельная шкала 0..100, в общий балл не входит**:
  `0.5 × пинг + 0.3 × стабильность (джиттер, 80 мс → 0) + 0.2 × доступность`
  восьми игровых платформ (Steam, Epic, Battle.net, Riot, PSN, Xbox,
  Nintendo) под стратегией с принудительно включённым игровым фильтром
  (2 круга проб; `internal/zapret/game.go`).
- Игровой подбор: пользователь сам выбирает стратегии для проверки чек-листом
  во втором шаге модалки (одна, несколько или все; по умолчанию все), тестируются
  только выбранные — на игровых ресурсах, применяется лучшая по игровому баллу
  (см. §3.2b). ПКМ-проверка одной стратегии — без игры.
  Результаты в таблице `strategy_games`.
- **Значок «игровая»** — игровой балл ≥ 60. Игровой фильтр включается
  только на стратегиях со значком: `SetGameFilter(mode ≠ off)` на остальных
  возвращает `game_mode_unsupported` + список игровых стратегий — UI
  показывает модалку отказа с этим списком и кнопками переключения.
- **ipset** (`ipset-all.txt`) — диапазоны IP серверов для winws; в балл
  не входит, но в статистике: число записей, битые строки, возраст
  обновления (`GetIpsetStatus`).

### 8a.6. Живые данные вкладки стратегий

- Вкладка стратегий обновляется живьём: событие `zapret:strategies-changed`
  (смена стратегии, игровой фильтр, ipset, завершение подбора) + поллинг
  10 с с паузой в скрытой вкладке. Переоткрывать вкладку не нужно.
- Режимы автоподбора — только «Умный» и «Игровой»: частичный подбор
  (mode=missing), классический полный перебор и еженедельный промпт полного
  прогона убраны (фоновые прогоны сознательно не делаются: тест переключает
  движок и рвёт трафик).

## 9. Мониторинг: правила сбора и хранения

### 9.1. Интервал

- Настраивается в config (по умолчанию 30 сек).
- Возможные значения: 15s, 30s, 1m, 5m.
- Слишком частый поллинг даёт ложные картины (DPI «глушит» при всплесках).

### 9.2. Хранение истории

- В SQLite: каждая сэмпл-запись = `{timestamp, resource, available, latencyMs}`.
- Окно хранения: 7 дней сырых данных, 30 дней агрегатов (часовые средние).
- Чистка по расписанию (раз в сутки).

### 9.3. Метрики для UI

- **Текущая доступность** — последнее значение.
- **График за час** — сэмплы за последний час.
- **График за день** — часовые средние.
- **Топ проблемных ресурсов** — ресурсы с наибольшей долей неудач за окно.

### 9.4. Проверка YouTube (DNS-уровень, ytcheck)

- Хосты: `www.youtube.com`, `redirector.googlevideo.com`.
- Метод: системный резолв vs DoH (dns.google → cloudflare-dns.com) + TLS-проба
  (:443, SNI) по полученным IP. Подмена = системный IP мёртв при живом
  DoH-IP (или пустой системный резолв при живом DoH).
- Каденция: такт ресурс-проверки + сразу после старта; результат кэшируется
  (`GET /api/youtube/status` без сети), событие `youtube:dns-issue` — при
  переходе в проблему, уведомление — один раз за сеанс.
- **Не входит** в общий % доступности и автоподбор/AutoSwitch: стратегии
  не чинят DNS.

### 9.5. Трафик: сессионные счётчики

- Счётчики интерфейсов — `GetIfEntry` (MIB_IFROW, 32-бит; `GetIfEntry2Ex`
  на windows/386 портит heap выравниванием uint64 — НЕ использовать).
- Учитываются только адаптеры с физическим адресом (не loopback, не
  pseudo-интерфейсы; фильтр по OperStatus НЕ применять — активные адаптеры
  часто в статусе Dormant).
- Итог = per-interface дельты **за сеанс приложения** (сброс счётчика — не
  скачок; переполнение 2^32 считается через границу).

### 9.6. Экономный режим: правила

- Конфиг: `power_saving` (мастер-тумблер), `power_level` (1 низкая /
  2 средняя / 3 максимальная), `power_threshold` (0 = «всегда», -1 =
  «от АКБ», иначе 10..50 % с шагом 5).
- **Мастер-тумблер выключен → режим никогда не активен.**
- `power.Active()` = мастер ∧ (порог «всегда» ∨ «от АКБ» ∧ не на зарядке ∨
  заряд батареи ≤ порога). На зарядке процент растёт выше порога — режим
  выключается сам. **ПК без АКБ** (BatteryPercent недоступен): пороги
  неприменимы, включение режима активирует его сразу.
- Уровень 1 «Низкая»: интервалы ×5 (трафик 2с→10с, ISP 60с→300с, устройства
  60с→300с, sync 15с→75с, снапшоты 5с→25с), ресурс-проверка 30 мин,
  фронт-опрос 2с→5с, пауза при скрытом окне, отключение декоративных
  CSS-анимаций.
- Уровень 2 «Средняя» (`MonitoringPaused`): + пауза мониторинга трафика
  (скорости в 0) и записей снапшотов в БД. UI: вкладки Монитор/
  Синхронизация серые с карточкой перехода в настройки.
- Уровень 3 «Максимальная» (`ServicesPaused`): + пауза трекера устройств,
  ISP-детекта, sync-маяка и приёма маяков.
- Каждый цикл переоценивает состояние **на каждом тике** — восстановление
  при выходе из режима автоматично, без перезапуска.
- Ядро (zapret, SOCKS5, DNS, tgproxy) экономным режимом не управляется.
- UI: индикатор-батарея в сайдбаре (источник — `power_saving`,
  `power_saving_level`, `power_saving_paused`, `power_battery` в
  `/api/status`).

## 10. Диагностика: чек-лист

При вызове «Диагностика» (вкладка или тост об ошибке), ZPUI прогоняет набор проверок и выдаёт отчёт с рекомендациями:

| Проверка | Условие | Рекомендация |
|---|---|---|
| Права админа | процесс повышен | «Запустите от имени администратора» |
| WinDivert загружен | драйвер в списке | «Переустановите zapret; проверьте антивирус» |
| Антивирус | детектируется | «Добавьте папку ZPUI в исключения» |
| zapret присутствует | файлы целы | «Переустановите zapret» |
| Стратегия валидна | файл стратегии существует | «Выберите другую стратегию» |
| Целевые ресурсы пингуются | TCP/TLS без обхода | «Провайдер не блокирует — проблема в чём-то ином» |
| С системным DNS | публичные DNS отвечают | «Проверьте настройки DNS» |
| Версия zapret актуальна | последняя | «Обновите zapret» |

Результат: список с зелёными/жёлтыми/красными маркерами и конкретными действиями.

## 12. Журналирование событий

В SQLite `events` пишутся ключевые действия (для истории и отладки):

- `engine.start` / `engine.stop` / `engine.crash` / `engine.restart`
- `strategy.applied` (id, source: manual/autoswitch)
- `autoselect.run` (winner, bestAvailability, duration)
- `autoswitch.triggered` (from, to, availability)
- `proxy.start` / `proxy.stop`
- `dns.start` / `dns.stop`
- `update.zapret.applied` (from, to)
- `update.zpui.available` (version)
- `diagnostics.run` (summary)

Срок хранения: 30 дней.

## 13. Пользовательские сценарии (компактно)

Полные сценарии — в [`Концепция.md`](./Концепция.md) §6. Здесь — их формализация в терминах бизнес-логики:

1. **Первый запуск:** стартовый экран → проверка системы → автоустановка движка (zapret2 скачивается сама) → умный подбор → применение.
2. **Ручной старт/стоп:** `engine.start` / `engine.stop`.
3. **Ручная смена стратегии:** `strategy.applied` (source: manual).
4. **Деградация без AutoSwitch:** виден низкий % на дашборде → пользователь открывает диагностику или запускает autoselect вручную.
5. **Деградация с AutoSwitch:** autoswitch triggered → engine restart → `strategy.applied` (source: autoswitch) → notification.
6. **Раздача на телефон:** proxy.start → клиент подключается → трафик идёт через WinDivert.
7. **Раздача на Xbox:** dns.start → консоль использует ZPUI как DNS → корректные ответы для Xbox Live.
8. **Обновление zapret:** update.zapret.applied → движок перезапущен.
9. **Обновление ZPUI:** update.zpui.available → «Скачать» (модалка с прогрессом) → «Установить» → закрытие приложения → запуск тихого обновлятора.

## 14. Краевые случаи и их обработка

| Случай | Поведение |
|---|---|
| Нет интернета при старте | Стартовый экран не может скачать zapret2: источник — сервер или GitHub (авто побеждает свежую версию); повтор после появления сети |
| GitHub недоступен | zapret2: сервер-зеркало продолжает отдавать релизы; ZPUI: сервер → при его недоступности Яндекс.Диск |
| Антивирус удалил WinDivert | `engine error` → диагностика предлагает переустановить |
| Параллельно запущен второй ZPUI | singleinstance: активировать первое окно, выйти |
| Порт 1080 занят | proxy.error → предложить сменить порт |
| Провайдер сменил DPI, стратегии устарели | autoselect не находит > порога → уведомление «обновите zapret» |
| Аккум нет (ноут без сети) | monitor: все ресурсы недоступны, % = 0, но AutoSwitch не сработает (есть smart-проверка на отсутствие сети) |
| Часы системы сбиты | TLS-рукопиатие падает → ложная «блокировка»; диагностика проверяет время |
