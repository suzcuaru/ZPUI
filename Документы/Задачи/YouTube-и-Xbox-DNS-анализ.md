# Анализ: YouTube не работает без Xbox DNS (zapret 1.10.x)

> Дата: 2026-08-28. Итог анализа бага «в новой версии Запрета YouTube работает
> только при включённом Xbox DNS» и описание реализованного решения (ZPUI 1.8.0).

## 1. Что происходит на самом деле

**Zapret (winws.exe) не имеет DNS-компонента.** Стратегии (`general*.bat`)
модифицируют пакеты уже установленных соединений — TLS/QUIC-фейки, disagoid,
multisplit. Ниже DNS они не работают: если системный резолвер отдал неверный
(IP-адрес для `youtube.com` / `*.googlevideo.com`), winws честно «обходится» с
тем, с чем соединится клиент, — а соединяться не с чем.

**«Xbox DNS» в ZPUI — это не локальный DNS-сервер**, а смена системного DNS на
все «Up»-адаптерах через `netsh interface ip set dns` на публичный сервис
**xbox-dns.ru** (`111.88.96.50` / `111.88.96.51`, значения захардкожены в
`internal/config/config.go` и forcируются при загрузке/сохранении). Этот
сервис возвращает рабочие (не отравленные) адреса для YouTube/Google.

**Почему в 1.10.x сломалось, а раньше «работало»:**

- В 1.9.x рабочие стратегии имели достаточный набор трюков, чтобы часть
  клиентских соединений попадала на «живые» IP из широких диапазонов
  (в т.ч. через QUIC-фейки по ipset), когда DNS ещё отдавал старые кэш-адреса
  или адреса из не полностью зачёрнённых подсетей.
- В 1.10.x рабочая комбинация стратегий (ALT/FAKE TLS AUTO/EXP из поставки)
  потеряла это свойство, а цензурный фильтр перешёл к связке
  «DNS-подмена + чернохолостинг IP-диапазонов googlevideo». В такой схеме
  никакой packet-трюк не помогает: нужен чистый резолвер. Отсюда зависимость
  «YouTube ⇒ Xbox DNS».

**Почему дашборд ZPUI был зелёным при сломанном YouTube:**

1. Мониторинг доступности проверяет только `lists/list-general.txt` — там
   **нет ни одного** YouTube/Google-домена (YouTube есть только в
   `list-google.txt`, который используется самим winws).
2. Проверки идут по системному резолверу: при включённом Xbox DNS резолв
   «починен», а TLS до корня домена проходит через фейкам winws. Подмена
   проявляется только на реальном воспроизведении (CDN-имена googlevideo).

## 2. Реализованное решение (1.8.0)

- **`internal/ytcheck`** — проверка DNS-уровня: `www.youtube.com` и
  `redirector.googlevideo.com` резолвятся через системный DNS и через DoH
  (dns.google → cloudflare-dns.com, JSON API), после чего делается
  TCP+TLS-проба (:443, SNI хоста) по полученным IP.
  - системный резолв пуст, а DoH отвечает → **подмена**;
  - системный IP не проходит TLS, а IP от DoH проходит → **подмена**.
- Запуск — в такт ресурс-проверки (`startResourceMonitor`) + сразу после
  старта; результат кэшируется, `GET /api/youtube/status` отдаёт его без сети.
- **Баннер на дашборде** при подмене: «Включить Xbox DNS» (кнопка вызывает
  `POST /api/xbox-dns/toggle`), Windows-уведомление — один раз на сессию при
  переходе в проблему (по тумблеру уведомлений об ошибках), событие
  `youtube:dns-issue` для мгновенного обновления UI.
- Проверка **не входит** в общий % доступности и не влияет на автоподбор/
  AutoSwitch: стратегии не чинят DNS, автопереключение при подмене только
  зря перебирало бы стратегии.

## 3. Возможные дальнейшие шаги (не реализовано)

- Добавить YouTube-строку на страницу «Мониторинг» с историей проверок.
- Кэшировать DoH-ответы и сократить количество внешних запросов.
- Рассмотреть собственный локальный DNS-прокси (DoH→:53) как альтернативу
  смене системного DNS адаптеров.
