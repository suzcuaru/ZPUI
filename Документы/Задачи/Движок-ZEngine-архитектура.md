# Движок ZEngine — архитектура (рабочее название)

> Статус: **проект, обсуждается** · Дата: 30.10.2026
> Контекст: решение о собственном движке ZPUI на Go, объединяющем DPI-обход (логика zapret/zapret2) и ускорение пинга в играх (подход lightspeed). Предварительные оценки — в сессии 30.10 (см. память проекта); лицензии проверены: **zapret/zapret2 — MIT** (портить можно, сохранить copyright-нотис), **lightspeed — Non-Commercial** (только чистая реализация по публичной документации, код не копируем).

---

## 1. Требования (ТЗ)

1. **Стратегии — не .bat**: декларативный формат, машинопригодный, валидируемый.
2. **Смена стратегии на лету** — без рестарта процесса.
3. **auto_list**: движок перехватывает трафик; если пользователь открывает ресурс, которого нет в списках — движок проверяет сам ресурс **и все его связи** (DNS, поддомены, CDN, API-серверы), определяет заблокированные и автоматически добавляет их в список обхода `auto_list`.
4. **Двойной режим**: полное подчинение приложению ZPUI; при этом способность работать автономно (без приложения).
5. **Интеграция** со службой ZPUI и текущим приложением (миграция со службы `zapret`, переключатель движков).
6. **CRUD стратегий на лету** — приложение/пользователь создал или поменял стратегию → движок подхватывает моментально.
7. **Фоновое тестирование стратегий** — без влияния на пользовательский трафик.
8. **Механизмы обхода из обоих проектов**: десинхронизация zapret2 (MIT) + игровой туннель lightspeed (чистая комната).
9. **Комбинирование стратегий** и одновременная работа «обычный режим + игровой».
10. **Списки** — серверные (загружаются приложением), в движке — встроенная база для автономной работы.
11. **Форма**: отдельный exe-модуль + глубокая интеграция с WinDivert. Сборка windows/386 обязательна (весь ZPUI — 32-бит), только pure Go + syscall (без cgo).

## 2. Общая архитектура

```
                    ┌────────────────────────────────────────────────┐
   ZPUI.exe         │                  zengine.exe                   │
┌───────────────┐   │  ┌──────────────────────────────────────────┐  │
│ internal/zeng │   │  │                core (ядро)               │  │
│ Manager-      │◄──┼──┤  lifecycle · генерации · hot-reload      │  │
│ супервизор    │   │  └──────────────────────────────────────────┘  │
└──────┬────────┘   │  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌──────┐  │
       │ named pipe │  │ divert  │ │strategies│ │ lists   │ │control│  │
       │ + status   │  │ WinDivert│ │компилятор│ │ 4 слоя │ │ pipe/ │  │
       │   .json    │  │ + потоковая│ │генерации │ │списков │ │status │  │
       ▼            │  │ таблица │ └─────────┘ └─────────┘ └──────┘  │
   /api/engine/*    │  └────┬────┘ ┌─────────┐ ┌─────────┐ ┌──────┐  │
   (web/src/api.js) │       │      │ desync  │ │ tunnel  │ │discover│ │
                    │       │      │ (zapret2)│ │ (games) │ │(auto_  │ │
                    │       │      └─────────┘ └─────────┘ │  list) │ │
                    │       ▼                              └──────┘  │
                    │   WinDivert 2.2.x (последний, x86+amd64)
                    └────────────────────────────────────────────────┘
```

**Процессная модель.** Один exe `zengine.exe`. Три способа запуска:
- **дочерний процесс ZPUI** (как winws сегодня) — основной режим, контролируется через named pipe;
- **служба Windows `ZPUI-Engine`** — замена службы `zapret` (миграция: RemoveService(zapret) → InstallService(ZPUI-Engine), та же схема реестра/SCM, что в `internal/zapret/service.go`);
- **автономный** (`zengine serve`) — без приложения: читает конфиг, сам синкает списки с сервером (opt-in), сам отвечает за восстановление.

**Статусы движка** (совместимы с UI): `stopped / starting / running / degraded / error / restarting` + отдельные статусы подсистем (tunnel, discover).

**Пакет в репозитории:** `cmd/zengine` (CLI-глаголы: `serve`, `service install/remove`, `probe`, `strategy validate/new`, `import`) + `internal/engine/*` (домены ниже). Вендоринг в сборку — `components/engine/` (zengine.exe + WinDivert.dll/.sys 1.4.x + встроенные списки), обновляется независимо от ZPUI.

## 3. Слой WinDivert (глубокая интеграция)

- **Биндинг**: чистый syscall через `syscall.NewLazyDLL("WinDivert.dll")` (паттерн `internal/power/power.go`) — без cgo, совместимо с windows/386. Драйвер — **последний WinDivert 2.2.x** (сейчас 2.2.2-A, официальный подписанный .sys рядом с exe; ре-дистрибуция легальна — LGPL/GPL с текстом лицензии). Что даёт 2.x:
  - **слои FLOW/SOCKET** — события установления соединений с привязкой к процессу: событийная атрибуция трафика вместо опроса таблиц сокетов (упрощает и игровой перехват, и discover);
  - **bulk-режим** получения пакетов — меньше системных вызовов в hot-path (winws2 уже использует его);
  - подписанные варианты, совместимые со всеми современными Windows (у 1.4 на новых сборках были проблемы типа high_entropy_va, которые bol-van чинил патчами DLL).
- **Фильтр-компилятор**: WinDivert-фильтр строится из активной конфигурации (порты web-стратегий ∪ UDP-профили игр ∪ UDP:53 для discover). Хендл держим на **супер-сете** (объединение всех известных потребностей) — обычная смена стратегии не переоткрывает хендл; переоткрытие только при расширении сета (миллисекунды, с drain).
- **Классификатор потоков**: шардированная flow-таблица (5-tuple → flow {зона: web|game|dns|own, генерация пайплайна, счётчики}). Fast-path — только lookup и маршрутизация; парсинг SNI/DNS-Host — в slow-path горутинах с ограничением очереди.
- **Защита от петли**: собственный PID движка и PID приложения исключаются из перехвата (probe-сокеты движка ходят напрямую).
- **Hot path**: `sync.Pool` буферов пакетов, zero-alloc в цикле, батчи где возможно, `GOMEMLIMIT`; метрики (pps, задержка, дропы) → status.json. Спайк фазы 0 отвечает за GC-латентность до старта основных работ.

## 4. Модель стратегий

### 4.1 Почему не .bat

Bat-стратегия — это аргументы командной строки winws: нет структуры, нет условий, нет метаданных, смена = рестарт процесса, парсинг хрупкий (в ZPUI ради этого существует `parseStrategyArgs()` с подстановками `%BIN%/%LISTS%`). Нужен декларативный документ, который: валидируется схемой, компилируется в план пайплайна, диффится, генерируется UI и сервером.

### 4.2 Выбор формата — варианты

| Формат | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **XML** | комментарии, XSD-валидация; в проекте уже есть опыт (`installer/manifest.xml`) | 2–3× многословие, тяжело писать руками и генерировать, устаревший выбор для новых конфигов | нет |
| **Lua** | выбор zapret2 → совместимость с их стратегиями; максимальная выразительность (условия, функции); комментарии | это **код, а не данные**: нужна VM (gopher-lua) и песочница, сложная валидация, «стратегия = программа» ломает декларативную модель, горячее диффирование и генерация из UI трудны, серверным Lua доверять нельзя без сэндбокса | не канон; только как **вход импортёра** |
| **YAML** | читаемый, комментарии, якоря/алиасы для переиспользования секций | сторонний парсер, ловушки (отступы, «no»→false, типы), легко сломать руками | фолбэк |
| **TOML** | Go-нативно, читаемо, комментарии | вложенные списки техник записываются громоздко, нет ссылок/якорей | нет |
| **JSON** | zero-dep в Go; каноничен для машины: UI генерирует, сервер раздаёт, движок мгновенно диффит; JSON-Schema валидация; **безопасен — данные, не исполняемый код**; детерминированный | нет комментариев (решаемо: читаем JSONC, пишем чистый JSON); многословен для ручного ввода; нет ссылок (решаемо `$ref`/`$include`) | **рекомендация: канон** |
| **Свой DSL** | идеально под модель (секции/слои/ссылки), краткий | парсер+валидатор+редактор+доки с нуля; юзеры не знают синтаксис; дублирует UI-редактор | опционально, фаза 4+: синтаксический сахар **поверх** JSON (компилируется в тот же канон), не вместо |

**Рекомендация: JSON (канонический «Strategy Document»), читается как JSONC** — комментарии и трейлинг-запятые допускаются на входе, канонический файл пишется чистым JSON. Лёгкий декларативный слой: `$ref` (ссылка на общий блок), `$include` (вставка файла/списка), параметры стратегий. Человек руками стратегии почти не пишет — редактор в ZPUI и сервер; автономный пользователь правит JSONC в блокноте, есть `zengine strategy validate/new`. Если захочется «свой формат» как продукт — делаем красивый текстовый синтаксис, компилируемый в этот же JSON.

### 4.3 Схема документа стратегии (пример)

```jsonc
// strategies/generic-fake-tls.json
{
  "meta": { "id": "generic-fake-tls", "rev": 3, "name": "Generic FakeTLS",
            "engine": ">=0.3", "source": "server" },

  "web": {
    "match": { "ports": [443, 80], "lists": ["core_blocked", "auto_list"] },
    "tls": {
      "trigger": "client-hello",
      "split": { "at": 1, "seqovl": 0 },
      "fake":  { "type": "tls", "count": 2, "ttl": 3, "payload": "builtin/fake-tls-ru.bin" }
    },
    "http": { "split": { "at": 1 } }
  },

  "game": null
}
```

```jsonc
// profiles/default.json — профиль = комбинированная конфигурация
{
  "meta": { "id": "profile-default", "type": "profile" },
  "web":  { "priority": ["auto-strategy", "generic-fake-tls"] },
  "game": {
    "profiles": ["cs2", "valorant"],                    // встроенные + пользовательские
    "tunnel": { "relays": "auto", "fec": { "k": 4 },
                "tcp_fallback": true, "probe": "rtt" }
  }
}
```

Ключевое отличие от winws: **пер-хостовые пайплайны**. Селектор стратегии (`match`) — это порты + списки хостов; классификатор выбирает пайплайн по SNI/Host конкретного соединения. Несколько web-стратегий живут одновременно (первое совпадение по приоритету), а не «одна глобальная секция --new». Комбинирование «обычный + игровой» — разные зоны одного профиля: TCP игры (маткмейкинг/авторизация) может идти через web-десинк, UDP — через туннель.

### 4.4 Компиляция и горячая замена (требования 2, 6)

- **Генерации (RCU)**: стратегия валидируется → компилируется в иммутабельный `Generation` (набор пайплайнов + дескриптор фильтра + ссылки на снапшоты списков). Реестр — `atomic.Pointer[Generation]`: публикация новой генерации атомарна, hot-path без локов.
- **Пиннинг потоков**: живые TCP-потоки доигрывают на зафиксированной у них генерации; новые соединения получают новую. UDP-сессии туннеля перепривязываются (смена релея = drain сессии). Старая генерация освобождается по обнулению ссылок.
- **Источники изменений** (все сходятся в один координатор):
  - команда по named pipe от приложения (`strategy.put/delete`, `set-profile`) — мгновенно;
  - файловый вотчер каталогов `strategies/` и `lists/` — пользователь/скрипты;
  - пуш списков от приложения.
- Невалидный документ **не** выкидывает движок: предыдущая генерация продолжает работать, ошибка отдаётся приложению (событие + status.json), т.е. смена стратегии атомарна и безопасна.
- **Импорт**: `zengine import zapret-bat general.bat` и `zengine import zapret2-lua <strategy>.lua` → канонический JSON. Даёт миграцию текущих пользовательских стратегий без потери (используем наработку `parseStrategyArgs()`).

## 5. Техники десинхронизации (порт zapret2, MIT)

Переносим алгоритмы из zapret2 с сохранением нотиса «Portions © bol-van, MIT»:

- **fake**: fake-tls (шаблоны ClientHello), fake-rst, fake-http; параметры count/ttl/badsum;
- **split**: сегментация TCP на позиции, `seqovl`, disorder;
- **ttl**: фейковые пакеты с малым TTL (умирают у DPI, доходят-нет до сервера — проверено blockcheck-методикой);
- **matching**: hostlist-матчинг по TLS SNI, QUIC SNI, HTTP Host; ipset/CIDR; exclude-списки;
- **QUIC**: fake-version и варианты начальных пакетов;
- объём порта определяем по **телеметрии ZPUI** (какие стратегии реально используются) — паритет с winws2 не нужен сразу.

Техника = интерфейс `Technique { Apply(*Packet, *FlowCtx) verdict }` в go-коде + декларативные параметры из стратегии. Никаких скриптов в горячем пути.

## 6. Игровой туннель (чистая комната по документации lightspeed)

- **Перехват**: UDP-потоки процессов игр (профили: `process_names`, `udp_ports`; встроенные ~24 игры — данные, не код). Атрибуция процесса: первично — события **SOCKET-слоя** WinDivert 2.2.x (событийно, без опроса), фолбэк — `GetExtendedUdpTable` (syscall, pure Go).
- **Redirect**: outbound пакет игры → туннельный сокет к релею; inbound от релея → реинжект с NAT-маппингом, игра видит оригинальный адрес сервера (IP-прозрачно, античит-совместимо; трафик не шифруем — как у lightspeed).
- **Протокол**: 20-байтный заголовок (version, flow-id, seq, ts, orig-addr) + XOR-FEC(k) + token-аутентификация + keepalive; control-план — plain UDP в v1, QUIC (quic-go, pure Go) — опция позже. TCP-fallback (length-prefixed framing) для сетей, где режут UDP.
- **Релеи**: собственный Go-релей (Linux, Docker на ZPUI-Server-инфре, 1–2 EU VPS); собственный **подписанный registry** (свой ключ, формат аналогичен их подходу по публичной документации); probing RTT/loss, авто-failover, режим «auto = лучший».
- **Диагностика**: аналог `--diagnose` — замер direct vs relay до сервера игры, вердикт «помогает/не помогает» в UI.
- **Одновременность**: зона `game` независима от `web` в классификаторе — «обычный обход + ускорение» работают параллельно из одного процесса и одного хендла WinDivert (это снимает главный конфликт двух отдельных движков — разные версии драйвера).

## 7. auto_list — автообнаружение блокировок (требование 3)

Конвейер `discover`:

1. **Пассивный сбор** (в hot-path бесплатно, эти парсинги и так нужны десинку): DNS-запросы/ответы (UDP:53) → карта домен↔IP с TTL; SNI из ClientHello и QUIC; HTTP Host. Сессия «визита»: после обращения к домену X окно 60 с собирает все домены/IP, куда реально стучится клиент (поддомены, CDN, API — всё видно на проводе, HTML-парсить не нужно).
2. **Кандидаты**: цель отсутствует во **всех слоях списков** (builtin / server / auto_list / user) **и не входит в листы исключений** → кандидат (rate-limit, cooldown). Ресурс из листов исключений не пробуется и не добавляется никогда.
3. **Активный проб** (вне горячего пути, собственные сокеты, PID исключён из перехвата): DNS-резолв (сравнение с системным), TCP connect, TLS-handshake с детекцией RST-инъекций (порт методики `blockcheck2` zapret2), HTTP-заголовок с детекцией заглушек-страниц, таймаут-профиль. Итог: вердикт `blocked/partial/ok` + уверенность; в auto_list квалифицируется только `blocked` — однозначные признаки (RST-инъекция, страница-заглушка, блок на DNS); `partial` никуда не добавляется, идёт только в лог/диагностику.
4. **Подтверждение с обходом**: повторный проб через тегированный пайплайн кандидата-стратегии — проверяем, что обход реально помогает (см. §8).
5. **Запись (молча, без модалок)**: домен (+IP/CIDR, если блок по IP) → `auto_list` (журнал изменений, атомарная запись, метаданные: источник/вердикт/время). Горячее применение: `auto_list` входит в `match` web-стратегий → следующий же пакет уже обходится.
6. **Гигиена**: периодический recheck записей (лёгкий), авто-удаление при `ok`; **политика пополнения — молча** (решено 30.10): только явно блокируемые ресурсы, отсутствующие во всех слоях списков, с обязательным учётом листов исключений (пользовательских и системных) — ресурс из исключений не пробуется и не добавляется.
7. **Синк**: события в приложение (UI показывает/редактирует auto_list) и на сервер (opt-in телеметрия → глобальная агрегация «народного» списка, раздаётся всем).

## 8. Фоновое тестирование стратегий (требование 7)

- **Probe-сессия**: стратегия-кандидат компилируется в отдельный пайплайн. Пробные соединения движка **тегируются** (локальный порт-диапазон/маркер в flow-таблице) и классификатор направляет их в probe-пайплайн вместо активного. Пользовательский трафик не затрагивается вообще.
- Измеряется: доля успешных TLS/HTTP, детект RST, RTT; по набору целей = key-ресурсы + сэмплы auto_list.
- Планировщик: простой машины/ночьной слот с уважением экономного режима (`internal/power`), либо по команде приложения; результаты → status.json + события → **существующий автоподбор ZPUI** (ScoreWeightedWithBase) получает баллы движка вместо перебора .bat.
- Тот же механизм обслуживает и игровую часть: probing релеев через туннель.

## 9. Списки (требование 10)

Четыре слоя, детерминированный мердж:

| Слой | Источник | Правка |
|---|---|---|
| `builtin` | встроен в exe (`embed.FS`): core_blocked, system-excludes | с релизом движка |
| `server` | загружает **приложение** с нашего зеркала и кладёт движку (app-режим); в standalone движок качает сам (opt-in) | hot-load |
| `auto_list` | движок (§7) | горячо, журнал |
| `user` | UI приложения / руками | горячо |

Форматы: winws-совместимые списки доменов и ipset/CIDR (совместимость = простой импорт) + расширенный формат auto_list с метаданными. Приложение — единственный канал сервера в app-режиме (движок без сети наружу, кроме проб и релеев).

## 10. Управление и интеграция с ZPUI (требования 4, 5)

- **Named pipe** `\\.\pipe\zpui-engine`, DACL SYSTEM+Administrators (паттерн SDDL-аудита 23.10). Протокол: length-prefixed JSON, verbs: `hello/status`, `subscribe-events`, `set-profile`, `strategy.{put,delete,list}`, `lists.put`, `auto_list.{query,edit,recheck}`, `probe.{start,stop}`, `tunnel.set-relays`, `engine.{reload,stop}`. Шина событий: `strategy:applied`, `auto_list:added`, `tunnel:relay-switched`, `engine:degraded`…
- **status.json** рядом с конфигом (heartbeat ~1 с): состояние, номер генерации, счётчики пайплайнов, RTT туннеля, статистика auto_list, кольцо последних ошибок (аналог `rememberOutput`). Устойчив к крашам — приложение читает файл, даже когда pipe мёртв.
- **ZPUI-сторона**: `internal/zengine` — Manager-супервизор по образцу плана tgproxy: spawn с backoff, health по status.json/pipe, обновление exe с бэкапом и откатом, проброс событий в UI через `runtime.EventsEmit`; маршруты `/api/engine/*` в `web/src/api.js` + вкладка управления (движок, стратегии, auto_list, туннель).
- **Переключатель движка**: «ZEngine | winws (zapret)» в настройках — winws остаётся фолбэком. Драйверы разных мейджоров (ZEngine — 2.2.x, winws — 1.4.x) имеют разные service names; переключение = полный останов одного движка → старт другого. Параллельное сосуществование двух загруженных драйверов — предмет проверки в спайке (фаза 0); в худшем случае сосуществования нет, но последовательное переключение работает всегда. Аварийный автоперевод на winws при `error` движка (политика настраивается).
- **Автономный режим**: `zengine serve` / служба без приложения; те же конфиги и списки, самосинк с сервера opt-in, single-instance mutex, самовосстановление.

## 11. Доставка и обновления

- `versions.txt`: поле `engine=`; `build.bat` собирает `cmd/zengine` (windows/386, ldflags-версия) в `dist/<ver>/engine/` (exe + windivert + builtin-списки + checksums).
- Обновление движка — как у `components/report`: приложение качает с зеркала сервера → Manager гасит движок → подмена exe с бэкапом → старт → верификация; откат при краше. Независимо от версии ZPUI.
- Версия движка видимая в UI (панель версий) и в телеметрии (opt-in).

## 12. Ограничения сборки (обязательные)

- **windows/386** — как весь ZPUI: `int` = 32 бита, только pure-Go зависимости, syscall-паттерн `NewLazyDLL` (WinDivert 2.2.x имеет x86-драйвер — ок). Негативный бюджет: quic-go и тяжёлые зависимости — только как опциональные фичи, не в базовой сборке без проверки 386.
- Фоновые циклы (discover-recheck, probe-планировщик, self-sync) — через `power.Stretch()`, уважение экономного режима.
- Логи — slog + `internal/logger`-стиль, ротация; никаких `fmt.Println`.

## 14. Риски и открытые вопросы

- **GC/латентность hot-path** — закрывается спайком фазы 0; на 386 окно памяти уже, следить за `GOMEMLIMIT`.
- ~~Политика auto_list~~ — решено 30.10: пополнение **молча**, только явно блокируемые ресурсы, отсутствующие во всех слоях списков, с учётом листов исключений (см. §7).
- **Нагрузка проб** на сеть/антивирусы: rate-limit по умолчанию, выключаемый.
- **Миграция службы** zapret → ZPUI-Engine на живых установках: нужен сценарий отката (переключатель движка его и даёт).
- **Релейная сеть** — появляется реальная ежемесячная стоимость (1–2 EU VPS); без релеев фаза 3 может стартовать в режиме «self-host relay» для энтузиастов.
- **Ресурс на сопровождение**: фиксы bol-van портируем по diff'ам (MIT) — дёшево, но нужен регулярный бюджет времени.

## 15. Решения, зафиксированные в этом документе

1. Канонический формат стратегий — **JSON (JSONC-чтение)** с `$ref`/`$include`; Lua/XML/TOML/YAML отклонены (обоснование §4.2); свой DSL — опциональный сахар поверх JSON в фазе 4.
2. Горячая замена — **генерации (RCU)** с пиннингом потоков; смена стратегии никогда не роняет движок.
3. WinDivert — **последний 2.2.x** (bulk-режим, слои FLOW/SOCKET для событийной атрибуции процессов, совместимость с современными Windows). Переключатель движков «ZEngine | winws (1.4.x)» работает через полный останов/старт; параллельное сосуществование драйверов — проверить в спайке.
4. auto_list — конвейер «пассивный сбор → проб → подтверждение с обходом → запись», с политикой подтверждения из приложения.
5. Туннель — чистая комната (лицензия lightspeed NC), релеи свои, registry свой подписанный.
6. auto_list пополняется **молча**: только ресурсы с однозначным вердиктом «заблокирован» (RST-инъекция / заглушка / DNS-блок), отсутствующие во всех слоях списков, с обязательным учётом листов исключений; `partial`-вердикты не добавляются (только лог/диагностика).
