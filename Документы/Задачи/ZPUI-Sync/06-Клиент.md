# 06. Клиент (ZPUI)

## 1. Архитектура контура отправки

Новый пакет `internal/sync` (или расширение `internal/app`), владеющий:

- **Тик 60 с + джиттер ±20%** (`time.Ticker` не годится — нужен пересчёт после
  `next_after`; экономный режим — `power.Stretch`, уровень 3 пропускает тики).
- **Планировщик секций:** таблица «секция → интервал → последний успешный ack»
  (флаги БД). На тике — просроченные, максимум 1–2 за тик, по старшинству.
- **Клиентская часть очереди:** хранит активный `ticket`; `busy` → тишина до следующего
  тика; `ok` → сдвиг курсора секции, удаление талона.
- **`sync.pull`** каждый тик: списки (`exclusions`, `dns_providers` — механика
  `stateSyncOnce`/`dnsSyncOnce` переезжает), `recommended`, `requests`.
- **HTTP-клиент** — общий с v4/v5 (таймауты, `SetCacheDir` не нужен — GitHub-кода нет).

## 2. Источники данных

| Данные | Кто собирает | Как |
|---|---|---|
| status, system, versions (частично) | **служба zsvc** | сама (статусы watchdog, файлы service.bat/версии) |
| availability, strategies, operator, events, traffic, network, errors, config, exclusions | **служба из SQLite/файлов** | читает рядом лежащие БД/config.json/skip-файлы (LocalSystem — доступ есть) |
| runtime (живое) | **приложение** | дублирует состояние в флаги БД при каждом изменении; служба отдаёт как last-known c `live: false`, либо форвард по pipe `zsvc.Client` с `live: true` |

SQLite из двух процессов: чтение службой при пишущем приложении — включить WAL
(проверить текущий режим пула в `internal/database`).

## 3. Этапность на клиенте

- **Этап A (в приложении):** контур sync живёт в приложении (цикл `stateSyncLoop` заменяется
  планировщиком секций). Служба не трогается. Релиз с этим этапом уже можно выкатывать.
- **Этап B (в службе):** цикл переезжает в zsvc (она уже установлена как Windows-сервис);
  приложение теряет фоновые отправки, остаётся поставщиком живых данных (кеш/pipe).
  Протокол не меняется — меняется только хозяин цикла.

## 4. Вкладка настроек «Данные и диагностика» (замена вкладки отчёта)

- Мастер-тумблер канала (включён по умолчанию, работает и без аккаунта — политика 11.2026; off = канал молчит).
- Статус: онлайн, последний тик, RTT, последний запрос сервера.
- Каталог секций (read-only состав) с **юзер-оверрайдами**: множитель частоты
  (×1/×2/×5) и «выключить секцию». Оверрайды умножаются на зашитые интервалы.
- Журнал запросов: «сервер запрашивал — что и когда» (из `sync.requests` + аудит).
- Кнопка «Сохранить снапшот в файл» — локальный экспорт всех секций (замена отчёту
  для ручной пересылки в поддержку).
- UI: токены дизайн-системы, i18n (ru/en), страница `ReportPage.jsx` сносится,
  новая — по конвенциям (hooks, `useT`, компоненты `components/ui`).

## 5. Снос в клиенте (чек-лист)

| Что | Где |
|---|---|
| Телеметрия v1 + отчёты | `app_server.go` (`StartServerTelemetry`, `telemetryLoop`, `sendServerTelemetry`, `sendServerReport`), `app_telemetry.go` целиком |
| Генератор отчётов | `internal/reports/` целиком, `app_api_reports.go` |

## 6. Известные ловушки (из истории проекта)

- **Бекап до правок** — `backup.bat`, обязательно.
- `wails build` без `-skipbindings` — иначе новые Go-методы не попадут в биндинги
  (шаг `web/check-bindings.mjs` в `build.bat` покрывает; карту маршрутов в `api.js`
  пополнять одновременно с биндингами, иначе кнопка молча мертва).
- Батники: скобки в `echo` внутри `if`-блоков ломают ветвление.
- Пул msedgewebview2 переживает exe — после пересборки убивать процесс целиком.
- Повышенный ZPUI не убивается из не-админ шелла (`taskkill`) — exe в dist не заменяется.
- Итоговые проверки: `go vet ./...`, `go test ./...`, `cd web && npm run build`,
  затем `build.bat` (полная сборка), посмотреть свежий dist.
- UI-работу принимать скриншотами живого окна (build ≠ приёмка).
