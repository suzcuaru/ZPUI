# 02. Протокол ZPUI Sync

## 1. Транспорт

Один эндпоинт:

```
POST /api/sync
Content-Type: application/json

{"op": "data.runtime", "dev": {...}, "token": "...", "payload": {...}, "ticket": "t_482"}
```

- `dev` — паспорт устройства (тот же, что у v4/v5: id, name, app_version, os, mac — `a.v5dev()`/`a.v4Device()`).
- `token` — аккаунт-токен устройства (как сейчас `AccountToken`); для неавторизованных операций (`sync.hello`) — пустой.
- `ticket` — талон очереди (см. §4), в остальных запросах отсутствует.

Ответ — единый конверт:

```json
{"ok": true, "data": {...}, "next_after": 300}
```
```json
{"ok": false, "error": {"code": "busy", "msg": "...", "ticket": "t_482", "retry_after": 45}}
```

Коды ошибок: `busy` (очередь записи полна, выдан талон), `auth_required`, `banned`
(токен отозван — клиент чистит AccountToken, как сейчас в `stateSyncOnce`),
`unknown_op`, `bad_payload`, `too_large`, `internal`.

## 2. Операции

| Группа | Операции | Назначение |
|---|---|---|
| Регистрация | `sync.hello` | регистрация/обновление устройства + presence + первичный обмен версиями |
| Данные | `data.status`, `data.runtime`, `data.availability`, `data.network`, `data.strategies`, `data.traffic`, `data.operator`, `data.errors`, `data.events`, `data.system`, `data.versions`, `data.config`, `data.exclusions` | 13 секций, форматы в 03 |
| Скачивание | `sync.pull` | серверные списки (исключения, DNS-провайдеры) + рекомендованные версии (zpui, zapret) — замена download-части `state.sync` |
| Просьбы | `sync.requests` | разовые «пришли секцию сейчас» (расширение `Request`-блока) |
| Позже | `auth.*`, `account.*` | портирование v4-аутентификации до релиза клиента (этап 2 миграции) |

## 3. Цикл устройства

- **Тик — 60 секунд** + **джиттер ±20%** (обязательно: размазывает волну из 1000 устройств).
- На тике: `sync.pull` (лёгкое чтение: списки, версии, requests) → отправка просроченных
  секций (`data.*`) → за тик не более 1–2 секций.
- `next_after` из ответа сервера уточняет момент следующего тика (рассинхронизация
  устройств, попавших в одну волну).
- Экономный режим (`internal/power`.Stretch) растягивает тик — как сейчас в `stateSyncLoop`.

## 4. Талонная очередь записи (admission control)

Семантика — «сначала спросить, можно ли отправить», но одним вызовом:

1. Служба шлёт `data.<секция>`. Есть свободный слот → сервер принимает (`ok`), тело обработано.
2. Слотов нет → сервер **не читает тело**, отвечает
   `{ok:false, error:{code:"busy", ticket:"t_482", retry_after:45}}`. Устройство ничего не выгрузило.
3. Устройство **сохраняет талон и молчит до следующего тика** (никаких агрессивных ретраев).
4. Повтор идёт с `ticket`. **Приоритет = время выдачи талона** (`issued_at`): освобождающийся
   слот отдаётся старейшему талону, а не свежему устройству — очередь «двигается», никто
   не голодает.
5. TTL талона (`sync.ticket_ttl_sec`, по умолчанию 600с). При истечении талон
   перевыпускается **с сохранением исходного `issued_at`** — место в очереди не откатывается.

Правила сервера:

- **Резерв для талонов** — 20% слотов обслуживают только талоны (иначе свежие устройства
  бесконечно перехватывают освобождающиеся слоты).
- **Presence обновляется на ЛЮБОЙ аутентифицированный запрос, включая busy** — очередь
  не должна «прятать» живые устройства из монитора.
- Ledger талонов ограничен (≈2× числа устройств), старейшие вытесняются.

Настройки (в админку CRM, ключи в `settings.go`):

| Ключ | Дефолт | Смысл |
|---|---|---|
| `sync_max_concurrent_writes` | 1000 | одновременные записи секций |
| `sync_ticket_ttl_sec` | 600 | жизнь талона |
| `sync_reserve_pct` | 20 | резерв слотов под талоны |

## 5. Нагрузочная модель (почему лимит — предохранитель, а не узкое место)

1000 устройств при дефолтных частотах (см. 03): `data.status` ~17 зап/с, `data.runtime`
~3,3 зап/с, остальные <2 зап/с суммарно → **~22–25 зап/с** постоянного трафика. Go-ядро
переваривает на порядки больше; запись секции — миллисекунды. Очередь реально срабатывает
при бурстах (массовое обновление парка в один вечер — все тикают синхронно) и деградациях.
Отсюда обязательность джиттера и `next_after`.

Трафик: < 0,5 МБ/сутки на устройство (статус ~170 КБ/сутки — основная часть).
На сервер при 1000 устройствах — примерно 13 ГБ/мес control plane.

## 6. Аутентификация и безопасность

- Каждая операция подписана `dev` + `token`; `banned` — устройство отключается от канала
  (клиент чистит токен, как сейчас).
- С 11.2026 (решение владельца) `data.*` и `sync.pull` работают и **без токена** — анонимно,
  по паспорту из `sync.hello` (Концепция §8, новая редакция): канал данных включён по
  умолчанию, гасится юзер-тумблером `channel_enabled` (клиент) и флагом `blocked` (CRM).
  Незарегистрированное устройство — `auth_required` до первого hello (hello идёт в начале
  каждого тика анонимного устройства); чужой отпечаток — `auth_required`. Аккаунт-операции
  (`auth.*`, `account.*`, `tunnel.*`, …) по-прежнему требуют сессию.
- Сервер логирует операции (аудит запросов данных — кто/когда/какая секция) для журнала
  запросов в клиентских настройках (см. 06) и безопасности.

## 7. Совместимость

Старые эндпоинты (v1 telemetry, v4, v5) живут на сервере **до сигнала владельца** «парк
обновился» (счётчик дропа старой телеметрии — индикатор готовности, см. 08). Клиент новой
версии говорит ТОЛЬКО на ZPUI Sync + v1-проверка обновлений при запуске (инвариант
обновляемости, см. 05).
