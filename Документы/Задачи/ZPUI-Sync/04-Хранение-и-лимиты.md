# 04. Хранение и лимиты

## 1. Принцип

Эндпоинты `data.*` — **писатели в таблицы**. CRM — только читатель (`SELECT`), никаких
парсингов JSON-блобов. Это позволяет не переделывать CRM-страницы, которые уже читают
таблицы, и полностью убрать слой парсинга отчётов.

Три режима хранения:

| Режим | Поведение | Для чего |
|---|---|---|
| **Факт (upsert)** | 1 строка на устройство (PK = device_id), пришёл новый — перезаписал. Не копится никогда | состояние «как сейчас» |
| **Поток с TTL** | append, чистится ротацией по дням | истории (доступность, события, ошибки) |
| **Поток уже есть** | существующие таблицы сервера без изменений | стратегии, события |

| `data.strategies` | `strategy_samples`, `strategy_game_samples` | есть | поток | `strategy_retention_days` = 90 (есть) |
| `data.traffic` | `device_traffic` | **новая** | upsert | — |
| `data.operator` | `operators`, `isp_aliases` | есть | upsert | — |

## 3. Схемы новых таблиц (ориентир)

```sql
CREATE TABLE IF NOT EXISTS device_runtime (
  device_id BIGINT PRIMARY KEY REFERENCES devices(id) ON DELETE CASCADE,
  zapret TEXT, strategy TEXT, zapret_uptime_sec INT,
  tgproxy JSONB, socks JSONB, xbox_dns BOOL,
  public_ip TEXT, local_ips TEXT[], live BOOL,
  collected_at TIMESTAMPTZ, updated_at TIMESTAMPTZ DEFAULT now());

CREATE TABLE IF NOT EXISTS availability_samples (
  device_id BIGINT REFERENCES devices(id) ON DELETE CASCADE,
  ts TIMESTAMPTZ, kind TEXT, ok INT, total INT, pct REAL,
  PRIMARY KEY (device_id, ts, kind));

CREATE TABLE IF NOT EXISTS device_errors (
  id BIGSERIAL PRIMARY KEY,
  device_id BIGINT REFERENCES devices(id) ON DELETE CASCADE,
  ts TIMESTAMPTZ, level TEXT, source TEXT, message TEXT);

CREATE TABLE IF NOT EXISTS device_config (
  device_id BIGINT PRIMARY KEY REFERENCES devices(id) ON DELETE CASCADE,
  hash TEXT, settings JSONB, updated_at TIMESTAMPTZ DEFAULT now());
-- аналогично: network_latest/network_samples, device_traffic, device_system, app_usage
```

## 4. Ротация — расширение существующего механизма

- Часовой `cleanupLoop` (`../ZPUI-Server/control/api/main.go:249`) уже чистит таблицы
  по ключам `*_retention_days` из `settings.go`. Новые потоковые таблицы добавляются в
  его map + новые ключи в `settings.go`: `availability_retention_days`,
  `network_retention_days`, `errors_retention_days`, `app_usage_retention_days`.
- Админка CRM получает ползунки автоматически (страница Settings уже рендерит retention-ключи).
- Мёртвые устройства вычищаются TTL'ом сами; в реестре остаётся строка `devices`
  с последним `last_seen`.

## 5. Дедуп и целостность

- Диффы могут задублироваться при ретрае (отправили → ack потерялся → отправили снова).
  Вставка: `INSERT ... ON CONFLICT (device_id, ts, kind) DO NOTHING` — повтор бесплатный.
- Курсор сдвигается устройством только после `cursor_ack` — потеря ответа не теряет данные.
- Пачки после офлайна ограничены размером (`too_large`), сверх — устройство прореживает.

## 6. Объём (1000 устройств)

| Таблица | Расчёт | Строк (потолок) |
|---|---|---|
| availability_samples | 48/сут × 1000 × 30д | ~1,4 млн |
| events | 4/сут × 1000 × 90д | ~360 тыс. |
| app_usage | 24/сут × 1000 × 14д | ~340 тыс. |
| device_errors | эпизодически | < 100 тыс. |

Для Postgres — незначительно; потолок фиксирован ротацией.

## 7. Снос после перехода

- Таблицы-блобы `reports` (`telemetry.go:107`) и `device_reports` (`device_reports.go:44`)
  + их viewer (`adminReportsList`/`adminReportGet`, `device_reports.go:159/186`) —
  удаляются по сигналу «парк обновился» (этап 4 миграции, см. 08).
- Их retention-ключи (`reports_retention_days`, `telemetry_retention_days`) уезжают вместе.
- CRM-страницы, читавшие блобы, к этому моменту уже переключены на таблицы (этап 2-3).
