# 08. План миграции

## 0. Общая последовательность

Парк = тестировщики: длинная совместимость не нужна, но снос старого — **поэтапный**,
чтобы сервер никогда не оказывался в состоянии «нечем принимать». Сервер строится
**рядом** со старым; клиент переезжает **одним релизом**; старое с сервера снимается
**по сигналу владельца**.

## Этап 1 — сервер: каркас `/api/sync`

- Диспетчер конверта (`op`/`dev`/`token`/`payload`), коды ошибок (02).
- Талонная очередь записи: semaphore + ledger талонов, настройки `sync_max_concurrent_writes`
  (1000), `sync_ticket_ttl_sec`, `sync_reserve_pct` — в админку.
- `sync.hello` + `data.status` (presence: любой аутентифицированный запрос обновляет
  last_seen, включая busy).
- **Готово, когда:** сервер видит онлайн-статусы тестовых устройств.

## Этап 2 — сервер: полный набор секций + CRM

- Все `data.*` (форматы 03) + записи в таблицы (04) + retention-ключи в cleanupLoop.
- `sync.pull` (исключения, DNS-провайдеры, recommended-версии) + `sync.requests`.
- **Портирование auth** v4 → `sync.auth.*` / `account.*` (логика `account_email.go`,
  `totp.go`, `recovery.go` — та же, новый конверт). Без этого клиент этапа 3 не сможет логиниться.
- CRM: панель профиля пол-экрана с подвкладками (07), чтение из таблиц; селектор периодов.
- Параллельно может идти этап 3 (клиент), контракты зафиксированы в 03.

## Этап 3 — клиент: релиз на ZPUI Sync

- Контур sync в приложении (06 §1-2): тик, планировщик, курсоры, талонная логика.
- Auth через `sync.auth.*`; списки через `sync.pull`; обновления — v1 (не трогается).
- Вкладка настроек «Данные и диагностика» (06 §4).
- **Снос клиентского старья** (06 §5): телеметрия, отчёты, `cmd/report`, v4/v5-код,
  GitHub-код zapret, ReportPage, выбор версии. Новый клиент говорит ТОЛЬКО на sync + v1-проверка обновлений.
- Релиз (`build.bat` → `release.bat`), владелец говорит тестерам «обновитесь».
- **Готово, когда:** все тестовые устройства на новой версии (видно по `data.status`).

## Этап 4 — сервер: снос старого (по сигналу владельца)

Индикатор готовности — счётчик дропнутой старой телеметрии: пока он растёт,
необновившиеся ещё есть. По сигналу «все обновились»:

- Удалить: v1-телеметрия (`telemetry.go`), v4/v5-хендлеры (`v5.go`, v4-роуты),
  приём отчётов, `reports` + `device_reports` (таблицы и viewer `adminReportsList/Get`),
  их retention-ключи.
- Оставить: `GET /api/v1/updates/zpui` + Яндекс-фолбэк (СВЯТОЕ), зеркало zapret.
- **Готово, когда:** единственный канал данных — ZPUI Sync.

## Этап 5 — клиент: переезд цикла в службу zsvc

- Цикл отправки переезжает в zsvc (читает SQLite/config/файлы сама; WAL для БД).
- Приложение: поставщик живых данных — дублирует runtime в флаги БД при изменении;
  форвард `live`-запросов по pipe (`zsvc.Client`).
- `app_running` от службы — уже в контракте `data.status`.
- **Готово, когда:** при закрытом приложении сервер продолжает получать данные
  (last-known с `live: false`) и точный presence.

## Этап 6 (опционально) — пробы и расширения

- `sync.requests.probe`: blockcheck по хосту / мини-тест стратегии (исполняет приложение).
- Поглощение остатков v4 (promo, подписки-эндпоинты) в sync по мере касания.

## Риски и откаты

| Риск | Митигация |
|---|---|
| Новый клиент не смог отправить (баг) | сервер держит старые эндпоинты до этапа 4; откат клиента — переустановка предыдущей версии через v1-обновления |
| Бурст после массового обновления | джиттер ±20% + `next_after` + талонная очередь (расчёт — 02 §5) |
| Очередь «прячет» живые устройства | presence обновляется на любой аутентифицированный запрос, включая busy |
| SQLite пишется приложением, читается службой | включить WAL; проверка пула (`internal/database`) |
| CRM сломается раньше, чем умрут блобы | порядок 07 §5: таблицы наполняются → CRM переключили → блобы снесли |
| Секреты утекут в телеметрию | каталог секций закрыт (03 §5); ревью payload по чек-листу |

## Явно НЕ делаем

- Серверное управление частотами (профили синхронизации) — частоты фиксированы.
- Постоянный WSS-канал — латентность до тика приемлема; конверт переносим на канал потом.
- Обратные команды управления (перезапуск движка и т.п.) — вне минимального скоупа.
- Совместимость клиента со старыми серверами / сервера со старыми клиентами после этапа 4.
