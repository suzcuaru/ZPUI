# 01. Обзор и решения

## 1. Цель

Заменить разрозненные каналы «устройство → сервер» одним протоколом **ZPUI Sync**:

| Сейчас | Станет |
|---|---|
| Телеметрия push (`POST /api/v1/telemetry`), всё одним куском раз в 30+ мин (`internal/app/app_server.go:211`, `app_telemetry.go`) | 13 секций `data.*` по фиксированным частотам |
| Диагностический отчёт — JSON-снапшот за 14 дней (`internal/reports/generator.go`), летит при старте/раз в час/после автоподбора | те же секции точечно; «пришли сейчас» — через `sync.requests` |
| Автономный модуль `cmd/report` (отдельный 32-битный exe) | сносится, наследника не имеет |
| Парсинг отчётов-блобов на сервере (`telemetry.go`, `device_reports.go`) | эндпоинты пишут в таблицы, CRM читает таблицы |
| Zapret: цепочка GitHub → зеркала → git clone в клиенте (`internal/zapret/updater.go`, `internal/updater/git.go`) | только сервер; GitHub из клиента удалён |
| CRM: просмотр отчётов-блобов (`adminweb/src/pages/Analytics.jsx:278`, `device_reports.go`) | панель профиля устройства на пол-экрана, данные из таблиц |

## 2. Принятые решения (полный список, сессия 23.10.2026)

1. **Новый протокол ZPUI Sync** — всё общение приложения/службы с сервером в конечном итоге идёт через него (один эндпоинт, один диспетчер, один конверт).
2. **Push от устройства** (служба шлёт сама), **посекционными запросами** — стратегии отдельно, операторы отдельно и т.д.
3. **Фиксированные частоты** на каждый тип данных (заранее настроенная система). Серверного управления частотами НЕТ.
4. **Разовые просьбы сервера** («пришли секцию сейчас») — расширение существующего `Request`-блока `state.sync` (сегодня там `{skips: true}`, `app_v5.go:163`).
5. **Талонная очередь на запись**: при исчерпании слотов сервер не принимает тело, а выдаёт талон; устройство повторяет на **следующем тике** (без спама ретраями). Приоритет очереди = время выдачи талона (fairness, никто не голодает). Лимит одновременных записей — настройка сервера, стартовое значение 1000.
6. **Онлайн-статус** определяется фактом прихода данных: любой аутентифицированный запрос обновляет presence, включая отклонённый по busy.
7. **`app_running`** передаёт служба (она и есть watchdog и знает статус приложения). Онлайн устройства = служба отправляет данные.
8. Цикл отправки в конечном счёте живёт в **службе zsvc**, не в приложении. Приложение — поставщик живых данных (кеш состояния в БД + pipe для форварда).
9. **Хранение**: эндпоинты пишут в таблицы; CRM только читает. Факты («как сейчас») — в единственном экземпляре, upsert на устройство, не копятся. Потоки (истории) — копятся с TTL-ротацией. Существующие `cleanupLoop` + `*_retention_days` переиспользуются и расширяются.
10. **CRM**: панель профиля устройства — пол-экрана, несколько подвкладок; подвкладка «Отчёт» показывает данные из базы (отчётов-блобов больше нет). Селектор периода: сегодня / 7 дней / 30 дней / произвольный период.
11. **Zapret качается только с сервера** (как и обновления ZPUI). GitHub из клиента удаляется целиком, включая выбор версии в UI. GitHub остаётся только на сервере (зеркало, цикл 6ч — уже работает).
12. **Парк = тестировщики.** Владелец скажет им обновиться; длинная совместимость с v4/v5 не нужна. То, что старые версии перестанут получать свежие данные, — принято как норма.
13. **Инвариант обновляемости (СВЯТОЕ):** путь «старый клиент увидел обновление → установил» живёт всегда: `GET /api/v1/updates/zpui` + фолбэк Яндекс.Диск. Этот эндпоинт **не переносится** в ZPUI Sync — бутстрап не должен зависеть от версии протокола.
14. Контроль плоскостей: **sync = control plane** (версии/хеши/URL, маленькие JSON), **скачивание файлов = data plane** (прямой HTTPS GET, бинарники через sync-диспетчер не гоняются).
15. Разовые пробы по требованию (blockcheck «проверь discord сейчас») — **этап 2**, не в минимальном скоупе.

## 3. Принципы

- **Каталог секций живёт на устройстве.** Сервер не может запросить то, для чего у устройства нет операции. Это граница приватности: состав и частоты зашиты, пользователь может ужесточать (оверрайды в настройках), но не сервер.
- **Диффы по клиентскому курсору.** Курсор хранится на устройстве (флаги БД), сдвигается только после `ok` от сервера. Офлайн — копится, отправляется пачкой с прореживанием.
- **Никаких секретов в каталоге** (см. 03, §«Границы каталога»).
- **Один тик — 1–2 секции**, чтобы не плодить одновременные записи и держать нагрузку ровной.

## 5. Ограничения и не-цели

- НЕТ серверного управления частотами (профиль синхронизации) — фиксированные частоты.
- НЕТ постоянного WSS-канала — латентность «пришли сейчас» = до одного тика (≈1 мин). Если когда-нибудь понадобится реалтайм, секции и конверт переносимы на канал без переделки.
- НЕТ переноса auth на первом этапе — вендор v4-аутентификации портируется в `sync.auth.*` до релиза клиента (см. 08, этап 2).
- НЕТ обратных команд управления (перезапуск движка и т.п.) в минимальном скоупе.
