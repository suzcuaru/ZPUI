## Очередь (не начато)

◐ **CRM Ресурсы: нет данных.** Причина: per-resource дневная статистика (resource_daily) приходила только из старых отчётов; в новом каталоге её нет. Решение: расширить `data.availability` полем `resources` (host/day/checks/pct из SQLite, курсор тот же) + таблица `resource_daily` в ядре + страница «Ресурсы» в CRM читает её. Затрагивает: core + клиент + crm/web.

☐ **Устройства туннеля (Happ-телефоны) как полноценные устройства.** Сейчас нигде не отображаются. Требования владельца: записывать данные туннель-устройства, помечать как устройство (**влияет на лимиты устройств по аккаунту**), запоминать между сессиями, показывать онлайн-статус. В CRM на странице «Устройства» — подвкладка «Устройства туннеля» (принцип как у обычных устройств, данные другие: UUID/Reality, трафик, последний handshake). Источник данных уже частично есть: core принимает /internal/reality/{uuids,traffic,online} от vpnctl, таблица tunnel_devices существует. Затрагивает: core (учёт в лимитах account.devices_limit!), crm (подвкладка), возможно клиент (показ в панели аккаунта).

☐ **DNS-провайдеры: серверный выключатель.** Владелец выключил провайдер (Xbox DNS) на сервере — в приложении он остался. Правило: клиент получает список системных DNS-провайдеров с сервера при запуске и периодически; провайдер, выключенный на сервере, **удаляется из списка устройства полностью**. Касается ТОЛЬКО системных; пользовательские не трогаем (о них только передаём информацию). Проверить: core dnsProvidersForSync — отдаёт ли только включённых и поднимает ли версию при выключении; клиент — заменяет ли список целиком (замена целиком уже была в control-логике). Затрагивает: core (фильтр/версия) + клиент (применение + UI не показывает выключенных системных).

## Сделано в этой волне оркестратором (Go-часть клиента)

- Пакетная отправка при запуске: первый тик после старта шлёт ВСЕ просроченные секции (без лимита 1-2/тик) — «данные подтягиваются при запуске».
- Дебаунс exclusions: изменение пользовательского скип-листа уезжает не позже ~60 с после ПОСЛЕДНЕГО изменения (dirty-since), а не первым тиком; веб-статус «отправлено/ожидание» — агентом A.
