# ZPUI Sync — проект нового протокола устройства↔сервер

> **Статус:** спецификация утверждена (сессия проектирования 23.10.2026), реализация не начата.
> **Исполнение:** планируется отдельной сессией/сессиями. Этот пакет документов — полный контракт на работу.

## Что это

Единый протокол связи ZPUI (приложение + служба) с сервером управления, заменяющий:
телеметрию v1 (`POST /api/v1/telemetry`), клиентские протоколы v4/v5, диагностические
отчёты (blobs) и модуль `cmd/report`. Сервер получает данные **секциями по фиксированному
расписанию**, с **талонной очередью** на запись и настраиваемой ротацией хранения.
CRM переходит на чтение таблиц (парсинги блобов удаляются).

## Быстрый старт для сессии-исполнителя

1. Прочитай `01` целиком, затем свой домен (`02`–`04` сервер, `06` клиент, `07` CRM) и `08` (этапы).
2. Затронуты **два репозитория** воркспейса: `ZPUI` (клиент, этот репо) и `../ZPUI-Server`
   (control/api — ядро и CRM adminweb). Соглашения — AGENTS.md каждого репо.
3. Правила неизменны: **бекап до правок** (`backup.bat` / `..\backup-all.bat`), затем
   `go vet ./...`, `go test ./...`, `cd web && npm run build`; для сервера — его собственные
   проверки (см. ../ZPUI-Server/AGENTS.md / README). Финальная сборка клиента — `build.bat`.
4. Коммитить без явного запроса пользователя нельзя (правило обоих репо).

## Ключевые решения (TL;DR)

- Один эндпоинт `POST /api/sync`, конверт `{op, dev, token, payload, ticket?}`.
- 13 секций данных с **фиксированными** частотами (без серверного управления частотами).
- Запись через **талонную очередь**: нет слотов → сервер отдаёт `ticket`, устройство
  повторяет на следующем тике; приоритет по времени выдачи талона. Лимит
  `sync.max_concurrent_writes = 1000` — настройка в админке.
- **Онлайн = любой пришедший аутентифицированный запрос** (включая отклонённый по busy).
- Эндпоинты **пишут в таблицы**, CRM только читает. Факты — в единственном экземпляре
  (upsert на устройство), потоки — с TTL-ротацией (механика `cleanupLoop` уже есть).
- Отчёты и `cmd/report` **сносятся целиком**; их замещают секции.
- Zapret качается **только с сервера**; GitHub из клиента удаляется, выбор версии тоже.
  GitHub остаётся только на сервере (зеркало). `GET /api/v1/updates/zpui` + Яндекс.Диск —
  **не трогать никогда** (инвариант обновляемости).
- Парк = тестировщики: длинная совместимость не нужна; v4/v5 сносятся после обновления
  парка (по сигналу владельца).
- Цикл отправки в итоге живёт в **службе zsvc** (она же шлёт `app_running`); приложение
  остаётся поставщиком живых данных (кеш/pipe).
