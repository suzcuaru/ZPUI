1. Требования к Центру обновлений и логированию
1.1. Расширенное логирование
В логах Центра обновлений должен отображаться подробный процесс: начало скачивания, прогресс загрузки (в % или МБ), факт успешного скачивания, процесс установки, статус завершения и возможные ошибки.
Логи должны быть доступны для просмотра в интерфейсе Центра обновлений.
1.2. Автоматическое обновление интерфейса
После успешной установки обновления интерфейс Основного приложения и Центра обновлений должен автоматически обновлять отображаемую версию. Ручное нажатие кнопки «Обновить страницу» не требуется.
Центр обновлений должен отправлять IPC-команду (событие) в Основное приложение об успешной установке, чтобы приложение актуализировало свой UI.
1.3. Уведомления
При запуске приложения, если доступна новая версия, необходимо показывать стандартное системное уведомление Windows (Toast-уведомление).
Проверка наличия обновлений для показа уведомления должна происходить строго при запуске приложения.
2. Архитектура хранения версий и фоновые проверки
2.1. База данных (БД) версий
Внедрить хранение актуальных версий (Основного приложения, модуля «Запреты» и других компонентов) в локальной БД.
Интерфейс Центра обновлений и Основного приложения должен считывать информацию о версиях непосредственно из БД. Это обеспечит динамическое (на лету) обновление данных в UI без перезапуска.
2.2. Механизм синхронизации и фоновые проверки
При запуске приложения (или по специальной CLI-команде) Центр обновлений должен проверять версии всех компонентов и записывать актуальные данные в БД.
Фоновая проверка: Основное приложение должно отправлять CLI-запрос в Центр обновлений 1 раз в час. Центр обновлений в ответе должен проверять наличие новых версий и, при их наличии, обновлять информацию в БД.
3. UX/UI: Действия после обновления модуля «Запреты»
3.1. Модальное окно принудительного авто-подбора
После успешного обновления модуля «Запреты» система должна показать пользователю модальное окно с текстом: «Необходимо пройти авто-подбор, чтобы данные были корректными».
В модальном окне должны быть две кнопки: [Согласиться] и [Отказаться].
При нажатии [Согласиться]: модальное окно закрывается, и автоматически запускается окно/процесс «Авто-подбора».
4. Новая функциональность: Привязка к Оператору и Авто-подбор
4.1. Определение оператора
Перед запуском «Авто-подбора» (в том числе при самом первом запуске) система должна автоматически определять текущего мобильного оператора связи.
На вкладке модуля «Запреты» в интерфейсе должен всегда отображаться текущий оператор.
4.2. Привязка данных и стратегий
Все данные, полученные в результате «Авто-подбора», должны жестко привязываться к конкретному оператору.
Цель 1: Формирование корректной статистики и отчетов в будущем.
Цель 2: Обеспечение независимости стратегий для разных операторов (для каждого оператора должен проходить свой авто-подбор).
4.3. Динамическое переключение (Hot-swap оператора)
Система должна отслеживать смену оператора (например, при смене Wi-Fi/сети на ноутбуке).
Критическое требование: При смене оператора приложение НЕ должно перезапускаться. Система должна в фоновом режиме понять, что оператор сменился, и мгновенно переключить UI.
При переключении оператора система должна:
Обновить отображение текущего оператора на вкладке «Запреты».
Переключить данные в подвкладках (отображать стратегии согласно уровню доступности нового оператора).
Автоматически сменить активную стратегию на ту, которая была сохранена для нового оператора.
Пример использования: Если на Операторе А была выбрана Стратегия 12, а на Операторе Б — Стратегия 8, то при физическом переходе на сеть Оператора Б система сама, без участия пользователя, переключит активную стратегию с 12 на 8.
4.4. Логика запуска Авто-подбора
При запуске приложения система определяет оператора.
Если в БД отсутствуют данные о прохождении «Авто-подбора» для текущего оператора, система автоматически инициирует его прохождение (по аналогии с существующей логикой первого запуска).
Примечание для разработчиков:
Обратите особое внимание на пункт 4.3. Отслеживание смены сетевого интерфейса/оператора без перезапуска приложения требует реализации отдельного фонового воркера (слушателя событий сети), который будет триггерить обновление UI-компонентов через реактивное состояние (state management) или события IPC.
