# Отзывчивость: старт, вкладки, DNS

## Проблема

### П1. Интерфейс «ключит/подвисает» после стартового экрана
- `web/src/App.jsx:600` — `pollStatus` каждые 2 с кладёт **новый объект** `status`; `pageProps` (App.jsx:967) пересоздаётся, т.к. `status` в deps → **все memo-страницы перерисовываются 30 раз в минуту** даже когда данные не менялись. Тяжёлые страницы (Dashboard с SVG-графиком, ZapretPage ~1200 строк) пересчитываются на каждом тике.
- Бэкендный `/api/status` (app_api.go:89) на каждый тик делает: `xboxDns.IsSetInSystem()` → 2 чтения реестра DNS адаптера (netif_windows.go:307), `autostartEnabled()` (реестр Run-key), `getLocalIPs`/MAC/hostname, при запущенном движке — SCM-запрос `GetServiceStatus`. Само по себе единицы мс, но вместе с фронтовым штормом даёт ощутимый фон CPU.
- Сразу после стартового экрана одновременно: первый тяжёлый такт проверки ресурсов, старт всех `usePolling`-хуков страниц, прогрев вкладок — конкуренция за CPU в момент монтирования UI.

### П2. «Погрузки» при открытии вкладок
- Страницы **размонтируются** при навигации (`App.jsx:1000`, `key={activePage}`) — всё состояние теряется, при возврате — снова скелетон/пусто → `await api(...)`.
- `DnsPage.jsx:52-54` — `cfg=null` до первого ответа (6 api-вызовов на маунт); `DashboardPage.jsx:15` — `loading=true` до первого ответа; MonitorPage/ProxyPage/ZapretPage — то же (до 17 вызовов на маунт у ZapretPage).
- Кэша между переключениями вкладок нет совсем.

### П3. Включение/переключение DNS — долго и без анимации
- `ToggleDnsProvider`/`ToggleDnsCustom` (app_api_xboxdns.go:377/414) — **полностью синхронные биндинги**: `syncDnsDoH` (netsh на каждый изменённый DoH-сервер, таймаут 15 с каждый, manager.go:604) → `applyDnsSources` → `xboxDns.Enable()`.
- `Enable()` (xboxdns/manager.go:305) держит **write-лок на всё применение**: pre-flight `probeServers` — **последовательные** пробы, до 3 с на сервер (netif_windows.go:417: UDP 1,5 с × 2 попытки) + netsh. Итог: переключение = 5–30 с; лок блокирует `GetStatus`/поллинг DNS-вкладки → интерфейс «висит».
- Фронт (`DnsPage.jsx:156-162`): тумблер переключается **оптимистично**, без pending-состояния строки — пользователь видит «включено», хотя применение ещё идёт. `Switch hideState`, никакого спиннера.

## Цель
Интерфейс после старта остаётся отзывчивым; повторное открытие вкладок показывает данные мгновенно; переключение DNS — с понятной анимацией процесса, не блокирует остальной UI и занимает секунды, а не десятки.

## Требования
- R1. При неизменном содержимом `/api/status` React-страницы не перерисовываются (обновление объекта — только при фактическом изменении данных).
- R2. `/api/status` не выполняет тяжёлые системные опросы (реестр DNS адаптера, автозапуск, network-факты) чаще раза в 3–5 с — TTL-кэш.
- R3. Вкладка, уже открывавшаяся в сессии, при повторном открытии показывает данные мгновенно из кэша; обновление — тихо, без скелетона. Первое открытие — скелетон допустим.
- R4. Во время применения DNS (провайдер, пользовательская запись, мастер-тумблер, DoH) соответствующая строка показывает анимацию «Включение…/Отключение…», повторное переключение строки заблокировано, по завершении показывается фактический результат (или ошибка с текстом).
- R5. Применение DNS не блокирует остальной интерфейс: опрос статуса и другие вкладки отвечают во время применения.
- R6. Pre-flight пробы DNS-серверов идут параллельно с общим дедлайном; DoH-изменения применяются без добавления последовательных 15-с окон netsh.

## Не-цели
- Keep-alive страниц (монтирование всех вкладок одновременно) — слишком большой реворк.
- Переход статус-дерева на контекст-селекторы (пересмотр контракта всех страниц) — вне этой задачи.
- Изменение интервалов поллинга (2 с статус, 12 с DNS — остаются).
- Серверная часть / канал ZPUI Sync.

## Критерии приёмки
- A1. В dev-сборке со счётчиком рендеров: при неизменном `/api/status` между тиками — 0 повторных рендеров активной страницы и модалок за 10 с.
- A2. `/api/status`: IsSetInSystem/autostart/network-факты берутся из TTL-кэша ≥ 3 с; длительность вызова GetStatus в логе < 30 мс (кроме первого).
- A3. Повторное открытие DNS/Монитора/Прокси в той же сессии: первый кадр с данными без сетевого ожидания (кэш), тихое обновление в фоне.
- A4. Тумблер DNS-провайдера: строка в состоянии «Включение…» (анимация) до события завершения; повторный тумблер строки заблокирован; итог — факт/ошибка.
- A5. Во время применения DNS опрос `/api/status` отвечает < 500 мс (лок менеджера не блокирует чтение статуса).
- A6. Включение провайдера с 2 живыми серверами: применение завершается ≤ ~4 с при нормальной сети (параллельные пробы с дедлайном 2 с).
- A7. Индикация применения уважает экономный режим (глушение декоративных анимаций; функциональный спиннер остаётся).
- A8. go vet/test, npm test/build — зелёные; build.bat собирает dist.

## План
Файлы: `internal/app/app_api.go` (TTL-кэш кусков GetStatus), `internal/app/app_api_xboxdns.go` (async-применение + события), `internal/xboxdns/manager.go` (сужение лока Enable, параллельные пробы), `web/src/App.jsx` (дифф setStatus через utils.deepDiff), `web/src/api.js` (+кэш-слой `apiCached`), `web/src/hooks/` (useCachedApi — SWR «кэш сразу + тихое обновление»), `web/src/pages/DnsPage.jsx` (+pending-состояния строк), страницы-потребители кэша (Dns/Monitor/Proxy/Dashboard).
Порядок: (1) бэкенд-кэш GetStatus → (2) дифф setStatus → (3) SWR-кэш + прогрев после старта → (4) DNS async+лок+пробы → (5) индикация на DNS-странице → (6) верификация по A1–A8.
Контракты: `/api/dns/*` POST возвращают `{applying:true}` мгновенно; событие `dns:apply` {phase: started|done|failed, scope, error} + поле `state` в `GetDnsConfig`.
Риски: дифф статуса — ложные «нет изменений» (глубокое сравнение уже есть в utils.deepDiff — переиспользовать); async DNS — конфликт параллельных переключений (сериализация очередью применений); лок Enable — корректность отката при ошибке.
