> Документ описывает техническую реализацию продукта: технологический стек, компонентную модель, потоки данных, жизненный цикл процессов, схему хранения состояния и сборочно-релизный конвейер. ## 1. Технологический стек

### 1.1. Backend (Go)

| Компонент | Технология | Версия (по `go.mod`) | Назначение |
|---|---|---|---|
| Язык | Go | 1.21+ | основная логика, все сетевые сервисы |
| Каркас приложения | **Wails v2** | v2.x | связка Go ↔ web-фронтенд; нативное окно с WebView2 на Windows |
| База данных | **modernc.org/sqlite** | — | чисто-Go драйвер SQLite (без cgo), хранит историю мониторинга и настройки |
| Логирование | `log/slog` (stdlib) + собственный `logger` | — | структурные логи в файл |
| HTTP-клиент | stdlib `net/http` | — | скачивание zapret, обновлений, проверка ресурсов |
| Сеть/DNS | stdlib `net/http`, `net` | — | HTTP-клиент, SOCKS5; переключение системного DNS — `internal/xboxdns` (dnsapi + netsh, plain IPv4) |
| SOCKS5 | собственная реализация в `internal/proxy` | — | раздача обхода на другие устройства |
| WinDivert-обёртка | вызов `winws2.exe` (zapret2) как дочернего процесса | — | движок обхода DPI |
| Трей/уведомления | Win32 API (`syscall`, `golang.org/x/sys/windows`) | — | иконка в системном трее, balloon-уведомления |
| Реестр Windows | `golang.org/x/sys/windows/registry` | — | автозапуск, ассоциации |
| Одноэкземплярность | `internal/singleinstance` (named mutex) | — | гарантия, что запущена одна копия ZPUI |

**Почему Wails, а не Electron / Tauri / чистый WinForms**

- **Electron** — тяжелый (Chromium + Node), ~150 МБ бинарник. Для утилиты «скачал-запустил» — перебор.
- **Tauri** — Rust + WebView, классный, но стек проекта — Go, а не Rust; переписывать backend нецелесообразно.
- **WinForms / WPF** — нативно для Windows, но UI рисуется кодом, медленно итерировать дизайн; нет реактивности.
- **Wails** — Go backend (вся логика на знакомом языке) + любой web-фронтенд (React, Svelte, Vue) в нативном WebView2. Размер бинарника ~10 МБ. Оптимально для десктоп-утилиты.

### 1.2. Frontend (web/)

| Компонент | Технология | Версия (по `web/package.json`) | Назначение |
|---|---|---|---|
| Каркас UI | **React 18** | 18.x | компонентная модель |
| Сборщик | **Vite** | 5.x | дев-сервер, production-бандл |
| Маршрутизация | **React Router v6** | — | навигация между вкладками |
| i18n | собственная обёртка `useT` + `locales/{ru,en}.json` | — | локализация |
| Стили | чистый CSS + CSS Custom Properties (переменные) | — | дизайн-система без Tailwind |
| Иконки | inline SVG-компоненты | — | векторная графика |
| Графики | легковесные canvas/SVG-компоненты | — | дашборд мониторинга |
| Тесты | **Vitest** | — | unit-тесты утилит и хуков |

**Почему чистый CSS с переменными, а не Tailwind / CSS-in-JS**

- Tailwind раздувает HTML utility-классами, затрудняет тематирование с-runtime-параметрами (у ZPUI динамические цвета из настроек).
- CSS-in-JS (styled-components, emotion) добавляет рантайм-накладные.
- CSS Custom Properties (`--bg-page`, `--text-primary`, `--accent`) нативно поддерживаются, переключаются в рантайме (тёмная/светлая темы), не требуют сборщика.

### 1.3. Инструментарий сборки и релиза

| Компонент | Технология | Назначение |
|---|---|---|
| Инсталляторы | **Wails-приложения** (`cmd/setup`, `cmd/updater`, `cmd/uninstall` + `internal/pkginst`) | установщик / тихий обновлятор / удалятор (NSIS выведен из эксплуатации) |
| CI/CD | **GitHub Actions** | `.github/workflows/release.yml` (публикация релиза; проверки — локально перед коммитом) |
| Локальная сборка | `build.bat` | оркестрация: bump версии → build frontend → build Wails core → build 4 модулей → упаковка в `build/dist/` |
| Релиз-скрипт | `release.bat` | интерактивный помощник релиза (tag, push, заметки) |
| Зеркало | **Яндекс.Диск** | фолбэк-канал установщиков ZPUI (zapret: сервер управления → GitHub) |

## 4. Слой бэкенда

### 4.1. Точка входа `main.go`

Минимальный: создаёт экземпляр `app.App` и передаёт его в `wails.Run()` с конфигурацией окна. Вся логика — в `internal/app`.

```go
// упрощённо
func main() {
    application := app.NewApp()
    err := wails.Run(&options.App{
        Title:     "ZPUI",
        Width:     960,
        Height:    640,
        AssetServer: ...,
        OnStartup: application.OnStartup,
        OnShutdown: application.OnShutdown,
        Bind: []interface{}{application},
    })
}
```

### 4.2. Ядро `internal/app`

**`App` struct** — центральный объект. Все его методы (`func (a *App) ...`) автоматически становятся доступны фронтенду как `window.go.app.App.*`.

Жизненный цикл:

1. `NewApp()` — конструктор, инициализация полей-зависимостей.
2. `OnStartup(ctx)` — вызывается Wails при старте. Здесь:
   - проверяется single-instance (named mutex);
   - открывается/создаётся SQLite, config.json;
   - инициализируется logger (открываются файлы в `logs/`);
   - создаётся иконка трея;
   - запускаются фоновые горутины (monitor polling, autostart check).
3. Бинд-методы обрабатывают запросы от фронтенда (синхронные или через `runtime.EventsEmit` для асинхронной передачи прогресса).
4. `OnShutdown(ctx)` — корректное завершение: останавливается winws2.exe, закрываются серверы (SOCKS5, MTProto-мост, DNS), flush логов, освобождается mutex.

**Группировка биндингов** — правило «файл = домен» (внутри `internal/app`):

| Файл(ы) | Домен |
|---|---|

**Ответы API** — единый формат через хелперы из `app_api_types.go`:

- `okResp(data)` → `{"status":"ok", ...data}`
- `errResp(msg)` → `{"error":"..."}`
- фронтенд проверяет наличие поля `error`.

### 4.3. Управление zapret (`internal/zapret`)

Единственный движок — zapret2: внешний процесс `winws2.exe` (bol-van/zapret2;
legacy zapret1/winws.exe выведен 14.11.2026). ZPUI им управляет через менеджер,
а не запускает DPI-обход сам. Все операции с процессами движка — методы
менеджера (`KillEngineProcesses`, `ResetWinDivertDrivers`), прямых taskkill из
`internal/app` нет.

- **`manager.go`** — высокоуровневое управление: старт/стоп, отслеживание PID, перезапуск при падении, восстановление после сбоя. Хранит активную стратегию, аргументы командной строки.
- **`service.go`** — обёртка над Windows Service API: zapret можно зарегистрировать как системную службу (чтобы работал до входа пользователя в систему и при перезагрузках). Здесь — установка/удаление службы, старт/стоп через Service Control Manager; на службе включается SCM-recovery (перезапуск при сбое процесса).
- **`install.go` / `updater.go` / `sources.go`** — единый канал обновления zapret2: `CheckForUpdatesVia` (updates_source) → `DownloadUpdateInfo` → `InstallDistArchive`; `InstallFromZip` со strict-guard (архив без winws2.exe отвергается). Установка arch-aware: 32-битный процесс кладёт `binaries/windows-x86` (WinDivert32.sys), 64-битный — `binaries/windows-x86_64` (WinDivert64.sys).

Поток запуска:

```
App.ZapretStart(strategy)
   └─ manager.Start(ctx, strategy)
        ├─ собрать CLI-аргументы из стратегии (фильтр-списки, опции)
        ├─ executil.Run("winws2.exe", args...)
        ├─ сохранить PID, подписаться на процесс (горутина wait)
        └─ вернуть статус во фронтенд
```

При падении winws2.exe (краш, OOM, антивирус) `manager` перехватывает событие, инкрементит счётчик рестартов и поднимает заново, если не превышен лимит; за пределами приложения движок страхуют SCM-recovery и watchdog службы ZPUI (§4.15).

### 4.4. Автоподбор стратегии

Логика автоподбора живёт в `internal/app` (оркестрация, фазы, стрим —
`app_autoselect_stream.go`) и `internal/zapret` (`autotest.go` — прогон и
скоринг стратегий, `gamefilter.go` — игровые порты/режим). Режимы —
`smart`/`game`/`startup`/`full`; источники кандидатов умного подбора:
сервер (`strategies.top`) → локальные данные оператора → все стратегии.
Прогресс — SSE-поток `/api/autoselect/stream` и события
`autoselect:event` / `autoselect:done` (фазы operator / server / local /
analyze / select). Доменные правила — [`Бизнес-логика.md`](./Бизнес-логика.md) §3.2–3.2b.

### 4.5. Единый стартовый экран (StartupScreen)

Мастера первого запуска нет: первый запуск (и запуск с устаревшей стратегией)
проходит через единый стартовый экран фронтенда (`web/src/components/
StartupScreen.jsx`, оверлей). Последовательность фаз — connect → health →
check-service → install → install-service → auto-select (всегда умный

`/api/envscan/scan` (окружение), `/api/zapret/install-engine` (авто-скачивание
zapret2, если дистрибутива нет) и service-маршруты;
шаги пишутся во фронтовый журнал. Правила фаз —

### 4.6. SOCKS5-прокси (`internal/proxy`)

Внутренний сервер на Go (stdlib `net`):

- слушает на настраиваемом порту (по умолчанию 1080);
- поддерживает авторизацию по логину/паролю (опционально);
- заворачивает исходящий трафик клиентов (телефонов, планшетов) в соединения, которые проходят через zapret (потому что winws2.exe перехватывает на уровне драйвера все исходящие пакеты машины);
- даёт клиентам «обход» без установки zapret на них самих.

### 4.6a. Telegram MTProto-прокси (`internal/tgproxy` + дочерний `ZPUI-TgProxy.exe`)

Сам мост — **отдельный дочерний процесс** `ZPUI-TgProxy.exe` (порт
[tg-ws-proxy](https://github.com/Flowseal/tg-ws-proxy), Python; исходники в
соседнем проекте воркспейса `../ZPUI-TgProxy`). Go-пакет `internal/tgproxy` —
**супервизор**: spawn/kill/watchdog дочернего exe, ready-гейт, парсер лога
(stats раз в 60 с и per-IP), рестарты при падении. Обе битности exe
поставляются в `components/tgproxy/`.

Логи — категория `tgproxy` (бакет `tgproxy_logs`); версия модуля —
`__version__` апстрима tg-ws-proxy (инжектится сборкой, карточка в центре
обновлений); состояние/статистика — `GetTgProxyStatus`, ссылки —
`GetTgProxyStatus.link/link_ee`, секрет — `RegenerateTgProxySecret`.

### 4.6b. Туннель ZPUI Live (подписка для телефона)

Встроенного VPN-клиента в приложении нет (wireguard-go/wintun не
используются). Приложение управляет подпиской туннеля для телефона: ссылки/QR
Happ, устройства аккаунта, перевыпуск ссылки, блокировка/удаление устройства —
`V4Tunnel*` (`app_tunnel.go`, маршруты `/api/account/tunnel*`); ноды и
балансировка — на сервере (`../ZPUI-Server`). Доменные правила —
[`Бизнес-логика.md`](./Бизнес-логика.md) §8a.2.

### 4.7. Системный DNS (`internal/xboxdns`)

Конфигурация — `config.xbox_dns`:
`{enabled, providers, custom, xbox_enabled}`. Локального резолвера нет —
в систему прописываются только **plain IPv4-адреса**.

- **`xboxdns`** — применение адресов из `EffectiveServers()` (пресет
  xbox-dns.ru + включённые базовые провайдеры + пользовательские записи) к
  **первичному физическому адаптеру**: применение — dnsapi с netsh-фолбэком,
  чтение состояния — реестр; перед первым применением снимается прежнее
  состояние адаптера, выключение возвращает снимок; активное состояние
  определяется фактом «в системе прописаны наши DNS» (внешнее изменение гасит
  тумблер), живость адресов проверяется фоном — если серверы не отвечают,
  DNS снимается сам; только IPv4 — статический IPv6-DNS при применении
  снимается в DHCP; легаси-поля (primary/secondary) мигрируют в
  `providers`/`custom` однократно при первом старте.

### 4.8. Мониторинг (`internal/monitor`)

Фоновая горутина:

- раз в N секунд (настраиваемый интервал) проверяет доступность пула ресурсов через HTTP(S)-запросы и TCP-коннекты;
- результат пишется в SQLite (история для графиков) и пушится во фронтенд через события;
- на основе метрики доступности может триггерить **AutoSwitch** (см. [`Бизнес-логика.md`](./Бизнес-логика.md)).

### 4.9. Проверка блокировок (`internal/blockcheck`)

Утилита, отвечающая на вопрос «заблокирован ли ресурс X прямо сейчас?»:

- TCP-коннект к хосту:443 с таймаутом;
- TLS-рукопожатие (проверка «оборвалось ли»);
- HTTP-запрос с анализом кода/тела;
- сравнение поведения с эталоном (прямое подключение vs через потенциальный DPI).

### 4.10. Обновления (`internal/updater`)

Два независимых направления, всё внутри самого приложения (отдельного модуля-обновлятора больше нет):

- **Обновление запрета (zapret2):** источники — **сервер управления**
  (манифест зеркала релизов апстрима: версия, URL из `uploads/`, SHA-256;
  `serverUpdateInfo`, `/updates/zapret2`) и **GitHub** (`bol-van/zapret2`,
  releases API; зеркала-прокси gh-proxy/ghfast сохранены). Режим «Авто» — оба,
  побеждает свежая версия. Установка — dist с overlay (arch-aware:
  windows-x86/windows-x86_64) с бэкапом состояния (списки, стратегия)
  в БД и откатом при ошибке.
- **Обновление ZPUI:** источники по приоритету — **сервер управления**
  (манифест: версия, SHA-256, имя файла, notes, force, is_test; файл из
  `uploads/`; `fetchServerZPUIManifest`), при его недоступности —
  **Яндекс.Диск**: установщик `ZPUI-Setup-<версия>.exe` из корня (без папок
  версий; версия определяется разбором имён файлов; легаси-имена
  `-win32.exe` прежних версий тоже распознаются), SHA-256 по
  `checksums.sha256`. Ответ сервера «обновлений нет» — окончательный (Яндекс
  в этом случае не ищется). Установка: ZPUI закрывается, detached-помощник
  PowerShell (`Wait-Process` по PID) запускает установщик поверх старой
  версии. Ключевые методы: `CheckZPUISetupUpdate`/`DownloadZPUISetup` (setup.go), `DownloadZPUISetup`/`DownloadZapretUpdate`/`ApplyZPUISetup`/`ApplyZapretPackage` (app_api_updates.go).
- Проверки выполняются **при старте** (через 10с) и фоновым циклом **раз в час**
  со случайным сдвигом ±5 мин (в экономном режиме интервал ×5) — по тумблеру
  `auto_update_check` (`startUpdateCheckLoop` под супервизором); результаты
  кэшируются в `updateFlags` (update_state.go) и читаются треем/панелью без сети.

### 4.11. Конфигурация (`internal/config`)

`config.json` — единственный источник истины настроек. Пакет разбит по
доменам: `config.go` (структура, Load/Save, Update/RView, дефолты,
миграции), `dns.go` (типы DNS и валидаторы), `zapret_prefs.go`
(движок/стратегия/фильтры), `proxy_prefs.go` (SOCKS5), `tgproxy_prefs.go`,
`server_prefs.go` (ZPUI Sync/аккаунт), `notify_prefs.go`, `autoswitch_prefs.go`,
`skip_resources.go` (skip-файлы), `paths.go`, `device_id.go` (ID устройства
в реестре). Загрузка — ленивая, с дефолтами; сохранение — через
`useDebouncedSave` во фронтенде (предотвращает лишние записи при дёргании слайдеров).

### 4.12. База данных (`internal/database`)

SQLite (pure-Go через `modernc.org/sqlite`). Схема — `db.go`, запросы —
по доменам: `queries_devices.go` (устройства сессии, соединения, снапшоты,
замеры Яндекс-инструментов), `queries_availability.go` (доступность ресурсов,
per-resource и daily-агрегаты), `queries_operator.go` (оператор, стратегии,

`queries_versions.go` (версии компонентов), `queries_metrics.go` (метрики
потребления приложения), `queries_backup.go` (слепок zapret, флаг обновления).
Чистка старых записей — по расписанию.

### 4.13. Трей (`internal/tray`)

- иконка в системном трее Windows с tooltip «ZPUI vX | стратегия | %»;
- контекстное меню: «Открыть ZPUI», статусные строки «Запрет/Прокси/Xbox DNS» (Прокси и Xbox DNS — тумблеры), «Обновление ZPUI — скачать» / «Обновление запрета — скачать» (видны только при наличии обновления; клик открывает окно с модалкой обновления), «Перезапустить», «Выход»;
- пункты обновлений читают кэш флагов (`Controller.HasZPUIUpdateAvailable/HasZapretUpdateAvailable`) — сетевых вызовов из цикла трея нет;
- «Перезапустить»/«Выход» уведомляют службу ZPUI (`app-restarting`/`app-exiting`), чтобы watchdog не счесть их крашем; если приложение зависло и само не отвечает — восстановлением занимается служба (см. §4.15).

### 4.14. Одноэкземплярность (`internal/singleinstance`)

Через Win32 named mutex: если ZPUI уже запущен, второй экземпляр обнаруживает занятый mutex, активирует окно первого и завершается.

### 4.15. Служба ZPUI (`internal/zsvc` + `cmd/service`)

Отдельный процесс `ZPUI-Service.exe` (каталог `components/service/`, версия —
поле `service=` в `versions.txt`): Windows-служба с именем **ZPUI**, учётка
LocalSystem, отложенный автозапуск. Берёт на себя автозапуск приложения
(создание/удаление задачи Планировщика `ZPUI`), «Запуск свёрнутым»
(`--hidden` в задаче) и watchdog — восстановление приложения после краша.

- **`service.go` (cmd/service)** — точка входа службы: SCM-интерфейс, IPC-сервер
  на named pipe, watchdog-цикл (тик 15 с).
- **`pipe.go`** — IPC-сервер; **`client.go`** (в internal/zsvc) — клиент
  приложения. Канал: `\\.\pipe\ZPUI-Service`, построчный JSON-протокол.

| Команда | Направление | Что делает |
|---|---|---|
| `ping` | app → svc | версия службы (сверка с `zsvc.BundleVersion`, инжектится при сборке ZPUI) |
| `status` | app → svc | состояние (`idle` / `watching` / `paused` / `failed`) |
| `set-autostart on/off` | app → svc | создать/удалить задачу Планировщика + реестр |
| `set-hidden on/off` | app → svc | флаг «Запуск свёрнутым»; существующая задача пересоздаётся с `--hidden` |
| `app-hello` | app → svc | приложение запустилось (pid, версия, hidden) |
| `app-exiting` / `app-restarting` / `app-updating` | app → svc | штатные события: watchdog не считает их крашем; updating — пауза watchdog с TTL |
| `restart-app` | app → svc | служба перезапускает приложение через задачу |
| `close-app` | app → svc | служба штатно закрывает приложение |

- **`watchdog.go`** — надзор за процессом `ZPUI.exe`: если процесс исчез без
  `app-exiting`/`app-restarting`/`app-updating` — это краш: служба пишет
  причину и рестартует приложение через задачу с паузами
  **1с → 5с → 15с**; **≥5 крашей за час** — статус `failed`, цикл остановлен
  до ручного запуска. На время обновления приложения watchdog ставится на
  паузу (`app-updating`, TTL). Приложение при краше службой **не** «подчищается»
  заодно с движком: winws2 переживает краш — за него отвечает `engineWatch`
  (ниже).
- **Мониторинг движка (`engineWatch` / `reviveEngine`):** тик проверяет службу
  «zapret»: установлена и автозапуск включён, а процесса `winws2.exe` нет
  **два подряд тика** — подъём через `net start zapret`, между попытками
  cooldown **90 с** (установка движка и cooldown-окно исключают ложные
  срабатывания). Снимок состояния — `EngineSnapshot` (installed/autostart/
  running/revives/last_revive), уходит в IPC-статус (`status`) как поле
  `engine`. На самой службе «zapret» включён SCM-recovery — перезапуск при
  сбое процесса.
- **`config.go`** — состояние службы в реестре **`HKLM\Software\ZPUI\Service`**
  (Autostart, Hidden, AppPath, ServiceVersion, Status, LastExitKind/At,
  CrashCount в окне 1 ч, WatchdogPausedUntil, LastCrashReason) — единственный
  источник истины для IPC-клиентов и watchdog.
- **`log.go`** — журнал службы: `<InstallDir>\logs\service.log` (фолбэк — рядом
  с exe службы).
- **Установка:** `pkginst.registerService` ставит службу при установке/обновлении
  (старые службы сносятся); при старте приложения модуль `svcStartup`
  (`app_service.go`) добивает установку при её отсутствии (только при
  повышенных правах и наличии exe в components), сверяет версию по `ping`
  и при несовпадении обновляет exe из `components/service/`, передаёт AppPath,
  однократно мигрирует автозапуск под службу. Всё best-effort: нет службы —
  тумблеры работают по прежней схеме задачи Планировщика. Деинсталлятор службу
  снимает.

### 4.16. Супервизор фоновых модулей (`internal/app/app_supervisor.go`)

Все фоновые циклы запускаются через `supervisedGo(name, fn)` (вместо `safeGo`):
`startup-cleanup`, `service`, `monitor`, `traffic`, `rotation`, `metrics`,
`resources`, `dns-watch`, `zapret-health`, `socks`, `socks-subnets`,
`server-ping`, `traffic-history`, `state-sync`, `xboxdns`, `update-check`,
`lists-auto`, `isp`, `netwatch`, `telemetry`.

- Паника в модуле: запись в реестр супервизора + лог через `log.Error`
  (показывает тост через существующий хук ошибок; прямых notify нет — чтобы
  не задваивать) + автоперезапуск с паузой **1с → 5с → 15с → 60с (cap)**.
- Более **5 рестартов за 10 минут** — модуль `failed` (не рестартует до
  перезапуска приложения); счётчик подряд сбрасывается после 5 минут
  стабильной работы. Статусы: `running` / `restarting` / `failed` / `stopped`.
- `GetModulesStatus()` → `/api/modules/status` — снимок для UI; секции
  «Фоновые модули» и «Служба» в отчёте.
- Ранее не останавливавшиеся циклы (`trafficHistoryLoop`, `netwatch`,
  телеметрия сервера) теперь выходят по `stopCh`.

`internal/notify.ShowThrottled(key, title, body)` — тост с дедупликацией по
ключу (окно 10 минут) — для повторяющихся уведомлений.

## 4a. Сервер ZPUI Live (`../ZPUI-Server`)

Серверная часть продукта (с 30.09.2026 — соседний проект воркспейса
[`../ZPUI-Server`](../../ZPUI-Server), свой git; деплой — Docker Compose).
Подробности деплоя, бекапов и restore — [`ZPUI-Server/README.md`](../../ZPUI-Server/README.md).

### 4a.1. Состав сервисов compose

| Сервис | Что делает |
|---|---|
| `control` | Go-API (stdlib `net/http`, PostgreSQL через `pgx`): клиентский `/api/v1/*` (аккаунты, устройства, VPN, стратегии, обновления, баннеры, телеметрия, тарифы), админский `/admin/api/*`, статика админки `/admin/`. При старте — лёгкие идемпотентные миграции схемы |
| `db` | PostgreSQL 16 + pgBackRest (WAL-архив, cron full/incr, verify-restore) |
| `admin` | nginx со статикой SPA админ-панели (`control/api/adminweb`) |
| `vpn` | WireGuard (UDP 51820) + сайдкар **vpnctl** (`:9103`, токен `INTERNAL_TOKEN`) в одном контейнере/NetNS: пиры (`wg`), шейпер (`tc htb`: корень — общий лимит подписки, классы на устройство — ceil = лимит устройства, rate = вес приоритета), счётчики трафика (`nft`) раз в минуту в control. `VPNCTL_FAKE=1` — тестовый режим без wg/tc |
| `guard` | edge-прокси (TCP :4430) с rate-limit: логин 10/мин, регистрация/смена пароля/вход в админку 5/мин, общий API |
| `backup` | бекапы pgBackRest + API-сайдкар `:9101` (control проксирует в `/admin/api/infra/backup/*`) |

### 4a.2. Схема портов

```
наружу:  TCP 4430 (панель/API через guard)   UDP 51820 (WireGuard, публикует сервис vpn)
внутри:  control :8080, db :5432, vpnctl :9103, backup-api :9101 (внутренние сети compose)
```

- `adminGate` пускает админ-API только с loopback/RFC1918/`100.64.0.0/10` (Tailscale);
  вход в админку — `POST /admin/api/auth/login` (логин+пароль, bcrypt → Bearer-сессия
  на 24 ч), legacy `X-Admin-Token` поддерживается переходно.
- Данные клиентов: ключи и IP устройств (`devices.vpn_pubkey/vpn_ip`), лимиты

### 5.2. Шим API (`src/api.js`)

Фронтенд НЕ делает HTTP-запросов к бэкенду (Wails работает в одном процессе, без встроенного HTTP-сервера). Вместо этого — единая функция-шим:

```js
// упрощённо
export async function api(method, route, body) {
    const fn = routeToBinding(route); // '/api/zapret/start' → app.ZapretStart
    return await fn(body);
}
```

`routeToBinding` — карта маршрутов: строка вида `GET /api/...` сопоставляется с конкретным `window.go.app.App.<Method>`. Все эндпоинты бэкенда регистрируются здесь же (см. [`AGENTS.md`](../AGENTS.md)).

**Преимущества:** единая точка для добавления эндпоинтов; одинаковая обработка ошибок; фронтенду не важно, HTTP это или IPC.

Помимо прямых вызовов биндингов, фронтенд подписывается на **события Wails** (`runtime.EventsOn`):

- `autoselect:event` / `autoselect:done` — прогресс и завершение автоподбора (фазы operator/server/local/analyze/select);
- `monitor:update` — новый сэмпл мониторинга;
- `update:available` — найдено обновление;
- `engine:progress` / `engine:done` — скачивание/установка движка zapret2;
- `toast:show` — показать уведомление.

Это позволяет бэкенду пушить прогресс долгих операций без поллинга со стороны UI.

## 6. Схема потоков данных

### 6.1. Поток «пользователь нажал Старт на дашборде»

```
[User click]
   └─ React: api('POST','/api/zapret/start', {strategy})
        └─ api.js: app.ZapretStart({strategy})
             └─ App.ZapretStart(payload) [Go, bound method]
                  └─ zapret.Manager.Start(ctx, payload.strategy)
                       ├─ сбор CLI-аргументов
                       ├─ executil.Run("winws2.exe", args...)
                       └─ return {status:"ok", pid:...}
   └─ React: обновляет UI (optimistic), показывает статус «Запущен»
   └─ Фоново: monitor продолжает поллинг, winws2.exe модифицирует пакеты
```

### 6.2. Поток «автоподбор стратегии»

Запуск — SSE-поток `/api/autoselect/stream?mode=smart` (или
`?mode=game&strategies=<csv>`); события — `autoselect:event` (фазы
operator/server/local/analyze/select + результаты) и `autoselect:done`.
Два режима: `smart` (умный) и `game` (игровой, список стратегий выбирает
пользователь).

```
[User: «Умный» (smart)]
   └─ stream mode=smart
        ├─ phase operator: определение оператора (isp)
        ├─ phase server: GET /api/v1/strategies/top?isp_key=…
        │    # персональный план или топ по рейтингу «оператор × стратегия»
        ├─ сервер недоступен/пуст → phase local: локальные данные оператора
        │    (история operator_strategies, до SmartLocalLimit лучших)
        ├─ локальных данных нет → все стратегии
        ├─ phase analyze: план теста (порог балла 70)
        └─ phase select: прогон группами → применить лучшую

[User: «Игровой» (game, чек-лист стратегий)]
   └─ stream mode=game&strategies=…  (фаза server пропускается)
        └─ for each выбранной стратегии:
             ├─ zapret.Manager.Start(strategy)
             ├─ проверка на игровых ресурсах (+ игровой балл)
             ├─ EventsEmit("autoselect:event", {…})
             └─ zapret.Manager.Stop()
        ├─ выбрать best по игровому баллу → применить
        └─ EventsEmit("autoselect:done", {mode})
   └─ Frontend (AutoSelectModal / StartupScreen): рейка фаз, live-результаты, провайдер
```

### 6.3. Поток «мониторинг и AutoSwitch»

```
[OnStartup горутина monitor]
   └─ каждые N сек:
        ├─ blockcheck.Check(allResources)
        ├─ database.WriteHistory(samples)
        ├─ EventsEmit("monitor:update", samples)
        └─ if availability < threshold && AutoSwitch on:
             ├─ autoselect.Run() (фон, с уведомлением)
             └─ tray.Notify("AutoSwitch: переключился на <strategy>")
```

### 6.4. Поток «обновление zapret» (сервер → GitHub)

```
[Старт приложения → checkUpdatesOnStartup (через 10с)]
   └─ zapret.Manager.CheckForUpdates()
        ├─ serverUpdateInfo()          — манифест зеркала на сервере управления
        │    (версия, URL из uploads/, SHA-256); ответ «обновлений нет» — окончателен
        ├─ в «Авто» — GitHub bol-van/zapret2 (тег + zip-asset; зеркала gh-proxy/ghfast)
        └─ updateFlags + событие update:available + тост
[User: «Скачать» (карточка/модалка/трей)]
   └─ app.DownloadZapretUpdate()
        ├─ DownloadUpdateInfo() — качает по UpdateInfo (сервер или GitHub,
        │   зеркала gh-proxy/ghfast для GitHub-ссылок)
        └─ события update:download{percent} … update:download-done
[User: «Установить» в модалке]
   └─ app.ApplyZapretPackage()
        ├─ saveBackupToDB() + SetZapretJustUpdated(true)
        ├─ zapret.Manager.InstallFromZip()
        │    ├─ CaptureState → thoroughCleanup (стоп службы/драйверов)
        │    ├─ extractUpdate (rename-трюк для занятых файлов)
        │    └─ RestoreState (списки + стратегия)
        └─ события update:install{step,percent} … update:install-done
```

Поток «обновление ZPUI» проще: `fetchServerZPUIManifest` (манифест сервера; при недоступности — `CheckZPUISetupUpdate`, имена установщиков на Яндексе) → `DownloadZPUISetup` (в %TEMP%, SHA-256: манифест сервера или checksums.sha256) → `ApplyZPUISetup` (Wait-Process помощник запускает установщик после выхода ZPUI).

### 6.5. Поток «телефон через SOCKS5»

```
[Phone Wi-Fi settings]
   └─ Phone → socks5://192.168.1.10:1080
        └─ proxy.Server (внутри ZPUI.exe)
             ├─ accept соединение
             ├─ парсим SOCKS5 CONNECT host:port
             ├─ net.Dial("tcp", host:port)
             │    ↑ этот dial перехватывается WinDivert (winws2.exe),
             │      модифицируются пакеты → DPI пропускает
             └─ bidirectional copy phone ↔ target
```

## 7. Управление состоянием

| Слой | Где | Что хранит |
|---|---|---|
| Время сессии (runtime) | `App` struct поля | PID zapret, активные серверы, подписки |
| Пользовательские настройки | `config.json` | стратегии, тумблеры, тема, интервалы |
| История и статистика | `SQLite` (`zappy.db`) | временные ряды мониторинга, события |
| Логи | `logs/*.log` | структурные slog-записи (ротация по дате) |
| Состояние UI | React state + hooks | текущая вкладка, формы, optimistic-флаги |

Принцип: **единственный источник истины для настроек — `config.json`**. UI — отражение этого состояния; изменение в UI → запись в config → реактивное обновление. Это гарантирует, что после перезапуска всё восстанавливается.

## 8. Жизненный цикл процессов

### 8.1. Запуск ZPUI.exe

1. `main.go` → `app.NewApp()`.
2. `wails.Run()` → инициализация WebView2.
3. `OnStartup(ctx)`:
   - `singleinstance.Acquire()` — если занято, активировать существующее окно и выйти.
   - `logger.Open()` — открыть файлы логов.
   - `config.Load()` — прочитать `config.json`.
   - `database.Open()` — открыть SQLite.
   - `tray.Create()` — иконка + меню.
   - Запуск фоновых модулей под супервизором (`supervisedGo`: монитор,
     трафик, служба ZPUI, обновления — полный список в §4.16).
4. WebView2 грузит собранный фронтенд (`web/dist`).
5. Фронтенд вызывает `app.GetConfig()`, `app.MonitorStatus()`, ... — строит UI.
   Если движок не установлен — поверх вкладок открывается
   стартовый экран (StartupScreen), который сам скачивает и ставит zapret2.

### 8.2. Запуск zapret

- По требованию пользователя (кнопка «Старт») ИЛИ автоматически, если в config включён автозапуск движка.
- `winws2.exe` запускается как дочерний процесс ZPUI.exe либо службой «zapret»; крах приложения движок не гасит — его поднимают SCM-recovery службы «zapret» и watchdog службы ZPUI (§4.15).

### 8.3. Завершение

- `OnShutdown(ctx)`:
  - `zapret.Manager.Stop()` — корректно завершить winws2.exe.
  - `proxy.Server.Stop()`, `xboxdns.Server.Stop()`.
  - `database.Close()`, `logger.Close()`.
  - `singleinstance.Release()`.
- Если zapret установлен как служба — он продолжает работать и после закрытия UI.

## 9. Безопасность

- **Права администратора** требуются для: запуска `winws2.exe` (драйвер WinDivert), прослушивания DNS-портов при раздаче, управления задачей Планировщика и службой ZPUI. Манифест приложения (`installer/manifest.xml`, подхватывается build.bat) запрашивает повышение через UAC.
- **Проверка целостности:** скачиваемые архивы сверяются по SHA-256 — манифест сервера управления, `checksums.sha256` (Яндекс), манифест релиза (GitHub).
- **Логи не содержат чувствительных данных:** пароли прокси не пишутся в открытый вид; IP-адреса пользователей не отправляются наружу.
- **Телеметрия — канал ZPUI Sync, включён по умолчанию у всех устройств**, включая неавторизованные (для умного подбора и диагностики; см. [`Концепция.md`](./Концепция.md) §8). Передачу отключает пользователь тумблером «Канал данных»; серверную функциональность целиком — `authorization_enabled`.
- **Лицензия — проприетарная EULA:** код закрыт; аудит — по согласованию с владельцем.

## 10. Сборка и релиз

### 10.1. Локальная сборка (`build.bat`)

Последовательно:

1. Чтение версий из `versions.txt` (без автоинкремента): `zpui`, `report`, `tgproxy`, `service`.
2. `cd web && npm install && npm run build` — production-бандл фронтенда.
3. `wails build` — сборка `ZPUI.exe` (встраивает `web/dist` через `embed.FS`).
4. Сборка модулей: report (`go build ./cmd/report` → `components/report/{report.exe,version.txt,checksum.sha256}`) и service (`go build ./cmd/service` → `components/service/ZPUI-Service.exe` + `version.txt` + `checksum.sha256`; копии в корни деревьев x86/x64).
5. Генерация `versions.json` (`zpui`, `report`, `tgproxy`, `service`) и `checksums.sha256`.
6. Копирование zapret и конфиг-файлов в `dist/<версия>/`.
7. Сборка инсталляторов (Wails, теги `desktop,production`): `cmd/setup` → `ZPUI-Setup-x.y.z.exe` (универсальный x86+x64), `cmd/updater` → `ZPUI-Update-x.y.z.exe`; хеши добавляются в `checksums.sha256` (NSIS-компиляция выведена из эксплуатации).

### 10.2. Версионирование

- **ZPUI core** — SemVer, источник истины `versions.txt` (поле `zpui`), бампится вручную.
- **report** — модуль с версией в `versions.txt` (поле `report`); `tgproxy` — константа, обновляется вместе с ZPUI; **service** (`cmd/service`) — поле `service` в `versions.txt`, инжектится ldflags при сборке и сверяется приложением с `zsvc.BundleVersion`.
- `versions.json` — собираемый артефакт (`zpui`, `report`, `tgproxy`, `service`; без ключа `selfupdate`; поле игнорируется при чтении в старых версиях).

### 10.2a. Раскладка Яндекс.Диска

Корень публичной папки: установщики `ZPUI-Setup-<v>.exe` (плоско, универсальные x86+x64), `checksums.sha256`, `components/report/`, папки `Zapret <v>/` и легаси `zapret/`. Папки версий `<v>/` не создаются (см. Бизнес-логика §8.3).

### 10.3. CI

Файл `ci.yml` в репозитории отсутствует (упоминался ранее, удалён). Проверки выполняются локально (`go vet ./...`, `go test ./...`, `npm run build`) и при локальной сборке `build.bat`.

### 10.4. Релиз (`release.yml`, ubuntu-latest)

**Важно:** этот job НЕ собирает бинарники (сборка Windows-нативная — Wails-приложение и Wails-инсталляторы, на Ubuntu невозможна). Он:

1. Реагирует на tag `v*.*.*`.
2. Берёт артефакты из корня репозитория (подготовлены `build.bat` + `release.bat` локально).
3. Формирует GitHub Release (установщик + portable zip; описание из CHANGELOG).
4. На Яндекс.Диск файлы заливаются вручную: установщик и `checksums.sha256` — в корень, `components/report/` — при изменении модуля.

Подробно — в [`AGENTS.md`](../AGENTS.md) и `GIT_WORKFLOW.md`.

## 11. Кроссплатформенные соображения

Текущая поддержка — **только Windows 10/11 (x86 и x64)**. Причины:

- WinDivert — Windows-only.
- Wails v2 поддерживает macOS/Linux, но движок zapret под них — другой (nfqueue на Linux, pf на macOS), что потребовало бы отдельного backend-слоя.
- Трей, реестр, named mutex — Win32 API.

Портирование не планируется (см. [`Концепция.md`](./Концепция.md), §9.2).

## 12. Производительность и ограничения

- **Память:** ZPUI.exe ~80–120 МБ (WebView2 + Go runtime). winws2.exe добавляет 10–30 МБ.
- **CPU:** в простое ~0%, при активном обходе — зависит от объёма трафика (DPI-модификация делается в ядре, эффективно).
- **Диск:** ~30 МБ бинарники + логи (с ротацией) + SQLite-история (чистится).
- **Сеть:** все пользовательские соединения проходят через WinDivert; дополнительные задержки — на фрагментацию TLS ClientHello (~миллисекунды).
