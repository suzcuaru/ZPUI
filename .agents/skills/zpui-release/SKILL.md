# Релиз ZPUI

## 0. Кто публикует

Релиз выполняет пользователь лично. Роль агента — подготовить всё к релизу; коммит, тег и push — только по явному запросу.

## 1. Версии

Источник истины — `versions.txt`, правится вручную:

```
zpui=<X.Y.Z>      # версия приложения, SemVer
report=<X.Y.Z>    # модуль cmd/report — бампить только при реальных изменениях
tgproxy=<X.Y.Z>   # модуль internal/tgproxy — аналогично
```

`build.bat` читает файл без автоинкремента, инжектит версии через ldflags и генерирует `versions.json` + `components/*/version.txt`. `versions.json` вручную не правится никогда.

## 2. CHANGELOG.md — перезаписать, не дополнить

CHANGELOG описывает **только текущую** версию; при бампе содержимое переписывается заново (старый блок удаляется, история живёт в `git log`):

```markdown
## vX.Y.Z

### Изменено
### Добавлено
### Исправлено
### Техническое   (по необходимости)
```

Дельту изменений сверяй с GitHub-релизом предыдущей версии (GitHub = истина о том, что уже ушло пользователям) и с фактическими изменениями; не переноси в новый блок пункты прошлой версии. Описание релиза на GitHub CI берёт из заголовка `## vX.Y.Z`.

## 3. Конвейер

1. **Проверки:** `go vet ./...`, `go test ./...`, `cd web && npm run build`.
2. **Сборка:** `cmd //c build.bat` → артефакты в `dist/<версия>/` (ZPUI.exe, report.exe, `ZPUI-Setup-<v>-win32.exe`, zapret, versions.json, checksums.sha256). Установщик попадает в `checksums.sha256` — приложение сверяет его перед запуском скачанного обновления.
3. **Релиз:** `cmd //c release.bat` — копирует `dist/<версия>/*` в корень, `git add -A`, коммит `vX.Y.Z`, тег `vX.Y.Z`, push. Только он — публикация через release.bat + CI; локальная сборка для тестирования.
4. **CI `release.yml`** (ubuntu-latest) НЕ собирает бинарники — он берёт артефакты из корня репозитория, пакует portable zip и создаёт GitHub Release с описанием из CHANGELOG. Поэтому корень должен содержать свежие артефакты.
5. **Яндекс.Диск (вручную, канал обновлений):** установщик + `checksums.sha256` — в корень папки (без подпапок версий!); `components/report/` — только если модуль менялся.

## 4. Правила коммитов

- Стиль conventional commits: `feat:`, `fix:`, `chore:`, `refactor:`, `docs:` (см. `Документы/GIT_WORKFLOW.md`).
- Не форсить, не amend, не rebase интерактивно, не делать пустых коммитов.
- Коммитить только по явному запросу пользователя.
- Перед коммитом проверь, что старые артефакты предыдущей версии удалены/заменены (в репозитории лежат exe текущей версии).
